# ADR 0010: Own Shared Intake Workspace Layout

## Status

Accepted

## Context

The intake workspace is shared by the root intake module and source modules.
Source modules need places to store their own source state and generated source
artifacts, but intake also needs durable cross-command state that source modules
must not own: SourceNameToCanonicalId records, shared update mutations, command
ledgers, command logs, and generated command IDs.

Commands are the public API, so workspace folders created for command execution
are command folders. Repository source and test files should mirror the same
command path structure; see ADR 0003 for the `src/cli/` and `test/` layout
rule.

Command folders are also the audit unit for logs, command envelopes, generated
artifacts, debug artifacts, and replay ledgers. See ADR 0013 for the
auditability rules.

## Decision

`$INTAKE_WORKSPACE` is the shared local workspace root. The root intake module
owns the `$INTAKE_WORKSPACE/intake/` subtree. Source modules may own their
assigned source-module subtrees, but they must not write intake-owned identity,
canonical, mapping, or replay state.

Root intake workspace layout:

```text
$INTAKE_WORKSPACE/
  intake/
    commands/
      <created-at>-<command-name>/
        <command-name>.Command.yaml
        <command-name>.DatabaseMutations.yaml
        <command-name>.log
    state/
      namespaces/
        <namespace>/
          <kind>/
            <encoded-metadata.name>.<kind>.yaml
```

Expanded examples:

```text
$INTAKE_WORKSPACE/
  intake/
    commands/
      2026-06-10T00-00-00-000Z-cabc123.../
        cabc123....Command.yaml
        cabc123....DatabaseMutations.yaml
        cabc123....ArtifactMutations.yaml
        ArtifactMutation/
          manual-correction-1.ArtifactMutation.yaml
        cabc123....log
    state/
      namespaces/
        mn-post/
          Agency/
            a2j40000000crR2AAI.SourceNameToCanonicalId.yaml
        intake/
          AgencyUpdate/
            agency-canonical-id.AgencyUpdate.yaml
```

Ownership determines the folder layout:

| Path                                                        | Owner       | Stores                                                                                                  |
| ----------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------- |
| `intake/commands/<created-at>-<command-name>/`              | root intake | command-local logs, command envelopes, debug envelopes, artifact mutations, and replay ledgers          |
| `intake/state/namespaces/<source-namespace>/<record-kind>/` | root intake | `SourceNameToCanonicalId` records that map a producer namespace plus source record key to canonical IDs |
| `intake/state/namespaces/intake/<update-kind>/`             | root intake | shared update envelopes keyed by canonical ID                                                           |

Workspace access is constrained by module namespace and by the command envelope
that authorizes the module execution. Cross-namespace reads and writes are
forbidden for every module unless an explicit root intake exception applies.

A non-root module may read or write only under one of these paths:

- `Command.spec.path`: the command-local output path assigned to that module
  execution
- `Command.spec.state.path`: the namespace-scoped state path assigned to that
  module

No other workspace access is allowed for non-root modules. A non-root module
must not read from or write to another module's namespace folder, must not read
from or write outside its assigned command path or state path, and must not
infer additional readable or writable paths from the process current working
directory, source artifact refs, or sibling workspace folders.

The root intake module may read from and write to any namespace command folder
when coordinating commands, including creating new namespace command folders.
That exception does not make source-module state folders globally writable; root
intake-owned cross-command state remains under `$INTAKE_WORKSPACE/intake/state/`
unless a command envelope explicitly grants another path.

For root intake commands, the assigned command and state paths are under
`$INTAKE_WORKSPACE/intake/`. For source modules, the assigned command and state
paths are under that source module's namespace folder. Source modules may choose
their own internal cache/state layout inside their assigned state path, but
cross-module communication must still use shared envelope IO and
the paths explicitly passed in command envelopes.

Command names are generated by the root intake module with
`@paralleldrive/cuid2`. Source modules do not choose command names for root
intake commands, and submodule command folders created as part of the same
execution use the same command name.

Command folders are named:

```text
<created-at-sortable-utc>-<encodeURIComponent(command-name)>/
```

The full command folder path is namespace-scoped:

```text
$INTAKE_WORKSPACE/<namespace>/commands/<created-at-sortable-utc>-<encodeURIComponent(command-name)>/
```

The command folder contains command-specific files: logs, debug envelopes,
prepared replay ledgers, command-local scratch files, and any artifacts that
only make sense for that command execution.

Command envelopes may contain paths that cross the envelope boundary, such as
`spec.path` and `spec.state.path`. Those paths should be absolute by the time
the command is handed to a source module. If a command writer accepts a relative
path as input, it must resolve that path against the command envelope's
directory before validation or execution and must persist the resolved path.

Paths embedded inside artifacts or database mutation ledgers remain
envelope-local. For example, `Artifacts.spec.artifacts[*].ref.path` is resolved
relative to the `Artifacts` file, and
`DatabaseMutations.spec.mutations[*].ref` is resolved relative to the
`DatabaseMutations` file. Envelope-local refs must not escape their parent
directory tree.

Cross-command state lives under `$INTAKE_WORKSPACE/intake/state/`. This includes
SourceNameToCanonicalId records, shared update mutations, lookup caches, and any
future state that must survive multiple command executions. Cross-command state
must be stored as Kubernetes-style envelopes with writer-owned file names.

Lookup caches include reusable resolver outputs. Resolver adapters used by
intake pipelines must be pure and cacheable. For database entity properties, a
reusable resolver cache envelope identifies the canonical entity identity,
target property name, source evidence, and resolved output. If a resolver
depends on mutable external data, that data dependency must be represented as
explicit typed input before the resolver is used by an import pipeline.

The `ResolvedProperty` cache subject identity for database entity fields is:

```text
apiVersion + canonical entity kind + canonical entity ID
```

The cache key also includes the target property name. Source evidence is stored
inside `spec.sources`, a map keyed by source namespace. Each source entry stores
source kind, source name, and a typed source-input fingerprint as provenance and
invalidation evidence. Those fields are not part of the cache identity, because
the value belongs to the canonical entity and must not vary by source module.

SourceNameToCanonicalId state is intake-owned. It lives under the producing source
namespace and the exact record kind being mapped:

```text
$INTAKE_WORKSPACE/intake/state/namespaces/<source-namespace>/<kind>/<encoded-source-name>.SourceNameToCanonicalId.yaml
```

`SourceNameToCanonicalId` stores only `spec.kind` and `spec.canonicalId`.
Type-specific cached fields such as slugs, coordinates, or relationship support
fields are not stored in this ledger.

Pure resolver output caches are intake-owned and namespace-scoped. Their exact
kind folder must match the cache envelope kind:

```text
$INTAKE_WORKSPACE/intake/state/namespaces/intake/<resolver-cache-kind>/<encoded-cache-key>.<resolver-cache-kind>.yaml
```

The encoded cache key is derived from:

```text
subject apiVersion + subject kind + subject name + target property name
```

The cache envelope `spec` must preserve those same components in structured
fields so the file name is never the only source of cache identity. When the
cache is backed by source evidence, `spec.sources` stores source-module-keyed
evidence entries.

Shared mutation state is intake-owned:

```text
$INTAKE_WORKSPACE/intake/state/namespaces/intake/<update-kind>/<encoded-canonical-id>.<update-kind>.yaml
```

Manual artifact mutations are intake-owned command-local workaround envelopes
stored in the root intake command folder for `intake import artifacts`. They do
not live in producer-owned source folders and are not cross-command state. A
command-level `ArtifactMutations` collection is named from the intake import
command name and may contain inline target mutations or relative `ref` items
to single-target `ArtifactMutation` envelopes:

```text
$INTAKE_WORKSPACE/intake/commands/<created-at>-<import-command-name>/<import-command-name>.ArtifactMutations.yaml
$INTAKE_WORKSPACE/intake/commands/<created-at>-<import-command-name>/ArtifactMutation/<mutation-name>.ArtifactMutation.yaml
```

Any folder that is kind-specific must use the exact envelope or record kind
value. Do not pluralize, kebab-case, lower-case, or otherwise transform kind
folder names.

Command logs are command-specific by default and should be written inside the
command folder as `<command-name>.log`. Do not write root intake logs to
`$INTAKE_WORKSPACE/logs/` by default. CLI metadata invocations such as `--help`
do not create command folders or command logs.

## Consequences

- Source modules can share a workspace with root intake without owning canonical
  identity state.
- Command output is inspectable and sortable by command execution time.
- Replaying or auditing a command can start from a single command folder.
- Cross-command state has one durable intake-owned location.
- Moving intake-owned mapping files out of producer workspaces avoids coupling
  source-module caches to canonical database identity.

## Alternatives Considered

- Store SourceNameToCanonicalId records under each producer workspace: rejected because
  canonical identity resolution is owned by intake, not by producers.
- Store logs under `$INTAKE_WORKSPACE/logs/`: rejected as the default because it
  separates logs from the command data they explain.

## Revisit Trigger

Revisit when remote workspace sync is implemented or when multiple root intake
modules need to share one workspace.
