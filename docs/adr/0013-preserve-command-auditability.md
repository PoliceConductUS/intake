# ADR 0013: Preserve Command Auditability

## Status

Accepted

## Context

Intake commands can call source modules, read and write YAML envelopes, resolve
source identities to canonical identities, apply manual corrections, write
database mutations, and emit replay ledgers. Operators need to audit what
happened later without reconstructing intent from terminal output or database
side effects.

Auditability needs one stable execution identity that follows the command
through root intake and any submodule calls. It also needs ordered command
folders, command-local logs, persisted operation envelopes, and replay ledgers
that can be applied in the same order.

## Decision

Every concrete command execution has one command name generated by the root
intake module. The command name is stable across all calls made as part of that
execution, including source-module command envelopes. Submodules must persist
that command name in their command envelopes and command folders; they must not
replace it with a local run ID.

CLI metadata invocations do not create audit artifacts. `--help` invocations
and argument parsing failures that happen before a concrete command is selected
must not create a command name, command folder, command envelope, log file, or
debug artifact. Once the CLI commits to executing a concrete command, even if
that command later fails validation, it must create the command name and command
folder and write command-local audit artifacts.

Command artifacts and logs are persisted under namespace-scoped command folders:

```text
$INTAKE_WORKSPACE/<namespace>/commands/<created-at-sortable-utc>-<command-name>/
```

The command folder is the audit unit. It contains the command envelope,
structured logs, generated artifacts, debug artifacts, manual workaround
envelopes when allowed, and command-local scratch/output files needed to
understand that command execution.

Structured logs are written to `<command-name>.log` in the command folder for
the command being executed. Root intake may also emit human-readable terminal
progress from the same log events, but terminal output is not the audit record.
Once a command folder exists, command-specific logs must not be written to a
workspace-root log file.

All durable operations must be persisted as Kubernetes-style envelopes before
or while they are applied:

- Source modules persist source-produced `Artifacts` and typed artifact
  envelopes in their namespace command folder.
- Root intake persists `Command`, `ArtifactMutations`,
  `DatabaseMutationsDebug`, `DatabaseMutations`, and
  `DatabaseMutationResults` envelopes in the root intake command folder.
- Intake-owned cross-command identity and canonical state is persisted under
  `$INTAKE_WORKSPACE/intake/state/`.

Command history is ordered by command folder name. The sortable UTC timestamp
prefix determines audit and replay order across namespaces. Replay must apply
`DatabaseMutations` ledgers in that folder order and must apply each
`DatabaseMutations.spec.mutations` array in stored order. Replay must not
recalculate dependency order from the current database schema. Replay writes
`DatabaseMutationResults` so each database mutation has an auditable success,
failure, or returned-value record.

Root intake may read from and write to namespace command folders to coordinate
commands and collect artifacts. Non-root modules may read and write only their
assigned command path and state path.

## Consequences

- A single command name traces the execution path through root intake and
  submodules.
- Command folders provide complete command-local evidence for audit and replay.
- Logs, inputs, corrections, outputs, debug files, and replay ledgers are kept
  together.
- Replay remains deterministic because command folder order and mutation order
  are stored, not inferred.
- Source modules can keep private state inside their own namespace state path,
  but cross-module audit evidence belongs in command folders and shared
  envelopes.

## Alternatives Considered

- Use separate submodule run IDs for each call: rejected because it breaks the
  execution trace unless every caller builds a secondary correlation system.
- Use a workspace-root log file as the audit record: rejected because it
  separates logs from the command artifacts they explain.
- Replay by scanning database relationships at replay time: rejected because it
  makes historical replay depend on the current schema instead of the stored
  command ledger.

## Revisit Trigger

Revisit when commands become distributed across machines or when command
folders need signed append-only indexes.
