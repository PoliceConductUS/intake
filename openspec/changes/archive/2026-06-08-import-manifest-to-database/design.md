## Context

The root intake project currently has a minimal `intake validate <manifest-ref>` scaffold. It does not yet validate full `ImportPackage` manifests, resolve canonical IDs, or write imported data to the database.

The requested change adds the first direct database import path for an existing source-produced manifest:

```text
intake import manifest /path/to/manifest.yaml
```

The first source namespace is `mn-post`, backed by `$INTAKE_WORKSPACE/intake/sources/mn-post/`. The current database already has the target tables and columns needed for the first supported entity families: `public.agency`, `public.officers`, and `public.agency_officers`, including agency and officer slugs plus agency location and coordinate columns.

The project invariant is that durable database IDs are never generated by the database. Imported canonical IDs may be assigned by intake only through a durable source-key mapping ledger.

## Goals / Non-Goals

**Goals:**

- Add `intake import manifest <manifest-ref>` to import an existing local `ImportPackage` manifest.
- Validate the manifest, mapping file, relationship references, `DATABASE_URL`, and database connection before writing rows.
- Resolve source entity keys into canonical database IDs from `$INTAKE_WORKSPACE/intake/sources/<namespace>/`.
- Assign and persist new mapping `canonicalId` values with `@paralleldrive/cuid2` for source keys missing from the mapping file.
- Transform supported manifest entities into current database rows and write them directly to the configured database.
- Create initial `$INTAKE_WORKSPACE/intake/sources/mn-post/` from the current MN POST manifest and `supabase/seed.sql` as implementation setup.

**Non-Goals:**

- Running source modules such as `intake import mn post`.
- Uploading, hydrating, or archiving source workspaces.
- General duplicate detection or candidate duplicate resolution.
- A CLI command for generating mapping files.
- Schema support for manifest fields that are not currently represented in the database unless the first manifest cannot be imported without it.

## Decisions

### Manifest import is the reusable pipeline

`intake import manifest <manifest-ref>` becomes the direct pipeline. Later source-module orchestration can produce a manifest and call the same code path instead of duplicating validation, mapping, transformation, and database writing.

### Mapping files are intake-owned YAML ledgers

The importer reads `$INTAKE_WORKSPACE/intake/sources/<namespace>/`, where `<namespace>` is `metadata.namespace`. For `mn-post`, the file shape is:

```yaml
agencies:
  <sourceAgencyId>:
    canonicalId: <canonicalAgencyId>
    slug: <agencySlug>
    locationPathId: <locationPathId>
    latitude: <agencyAddressLatitude>
    longitude: <agencyAddressLongitude>
personnel:
  <sourcePersonnelId>:
    canonicalId: <canonicalPersonnelId>
    slug: <personnelSlug>
agencyPersonnel:
  <sourceRosterId>:
    canonicalId: <canonicalAgencyPersonnelId>
```

Mapping records contain intake-owned resolution data. Source entities contain source-owned data. The importer combines both into database rows.

### Missing canonical IDs are assigned before database writes

If the manifest contains a source entity key with no mapping record, intake creates the required object mapping record and assigns its `canonicalId` with `@paralleldrive/cuid2`. For mapping record types that need additional intake-owned fields, those fields must be present before writing database rows. This means a new agency without `slug`, `locationPathId`, `latitude`, or `longitude` cannot be inserted until the mapping file is completed.

The updated mapping file is persisted before database writes so a failed database insert does not lose canonical ID assignments.

### Fail-fast validation happens before mutation

The command performs all read, schema, reference, mapping, and connection checks before database writes. It must fail before any database mutation when:

- The manifest is unreadable or malformed.
- `apiVersion` or `kind` is unsupported.
- `metadata.namespace` is missing.
- The mapping file is unreadable or malformed.
- A required mapping field is missing.
- An `agencyPersonnel` record references an unmapped agency or personnel.
- `DATABASE_URL` is missing.
- The database connection cannot be established.

The command must not report success after a partial import.

### Database writes target only current supported tables

Supported transformations are:

- Manifest agencies plus agency mapping records write to `public.agency`.
- Manifest personnel plus personnel mapping records write to `public.officers`.
- Manifest agency-personnel records plus relationship mapping records write to `public.agency_officers`.

Agency-personnel `agency_id` and `officer_id` are rewritten from source keys to canonical IDs through the same mapping file. Unsupported manifest fields are ignored for database writes.

## Risks / Trade-offs

- [Risk] Persisting new canonical mappings before database writes can leave mappings for rows that failed to import. -> Mitigation: This is acceptable because identity assignment is durable intake state; the command still reports failure and does not claim import success.
- [Risk] Direct inserts may trip unique constraints or foreign keys. -> Mitigation: Do not add `ON CONFLICT`; fail loudly so mappings or source data can be corrected.
- [Risk] Missing agency resolution fields block new agencies. -> Mitigation: Treat mapping records as the intake-owned resolution ledger and fail before writes when required fields are absent.
- [Risk] Manifest validation can drift from producer output. -> Mitigation: Add fixture coverage using the current MN POST manifest and keep the importer permissive only for unsupported extra fields.

## Migration Plan

No database schema migration is expected unless implementation proves a current MN POST field is required and has no existing target column. This change does require adding `@paralleldrive/cuid2` and a PostgreSQL client dependency if no existing dependency can connect through `DATABASE_URL`.

No generated type refresh is expected unless schema changes become necessary. No production migration plan is expected for the proposal as written. A local database reset remains useful validation because the initial mapping file is derived from current seed rows and must reference existing `location_path` rows.

Rollback is limited to removing the CLI command and mapping file changes before use, or reverting the implementing commit after use. Once mappings are used for real imports, canonical source-key assignments should be treated as durable state rather than casually regenerated.
