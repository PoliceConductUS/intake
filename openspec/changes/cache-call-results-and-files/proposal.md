## Why

Intake has one cache, the resolved-property cache of ADR 0019. Two sources and the `photo` command kept caches of their own beside it, each with its own files, keys and rules: CourtListener (search results, summaries, hand-review results, PDFs per command folder), Minnesota POST (document text and analysis, PDFs per command folder) and personnel photos (files with no envelope). None records a failed call, so a failure is retried on every run or stops the run. None records enough to reproduce a call. Files are downloaded again by later commands.

## What Changes

- **One cache.** There is one way to cache (owner's ruling, 2026-11-19). A call result is an entry of the resolved-property cache: under the record the call is made for, with the client operation as its property, keyed by the fingerprint of the request. The entry holds the request and the list of outcomes, success or failure: what a developer needs to reproduce the call (the service, the model asked for and the model that answered, the parameters including the reasoning level, the prompt text, the hashes of the inputs, the answer or the error, the provider's request ID, the times). It never holds a key. A changed document or prompt is a new entry; a changed model is not. The `CallResult` envelope and its store, built in commit 7275ec3, are replaced by this; none was written in any workspace.
- **A file is a record like any other.** `BinaryFile` is one record kind with one spec and the standard envelope IO, source-name mapping and folders: SHA-256, extension, content type, byte count and workspace path. The bytes are stored on disk by namespace, never in the database. A record that has a file points at it with a foreign key. The website reads a file's row and its workspace path, as it reads `personnel_photo` today.
- **One rule for calling again.** An outcome may carry `retryAfter`. Until then it stands; after it the call is made again. An item failure stands for 24 hours. A bad stored result is retired by an `intake cache` operation with `--message`, never deleted. `data reset --no-acquire` uses the last success even when a later attempt failed.
- **One client per service.** A CourtListener client, an inference client, a file download client and a PDF text client live in shared code. Each wraps the cache, checks its service before its first call that the cache does not answer (the inference check also confirms the model exists), retries, and tells a failure of one item from an outage: after the retries it checks the service again before calling it down, and key, account and credit errors count as an outage. Every source that calls these services uses the same ones, except `requests sync` and the news inference, which keep calling a model themselves. Until `cache-every-acquire`, the Census gazetteer, Oregon DPSST, Minnesota POST and Wikipedia federal agencies acquires still fetch outside the cache, and until the Minnesota task the Minnesota acquire still downloads, extracts text and requests analyses itself.
- **An acquire with failed or skipped calls fails at its end.** It makes every other call, so their answers are kept, then exits non-zero naming each failed or skipped call, and is not recorded as completed. An empty search result is a success. A service that fails its check stops that source's work and the command exits non-zero (`data update` first goes on with its next source). In `data generate`, `data update` and `data reset`, an outage skips the calls that need the service, changes nothing they would have filled, and the command prints the skips and exits 0.
- **`PersonnelPhoto` is retired.** A person points at their photo's `BinaryFile` with `photo_id`, set by a manual update that the manual source now handles. This change alone moves `assets/PersonnelPhoto/` and sets `photo_id`; `keep-state-under-one-root` and `import-personnel-photos` refer to it.
- **`data generate` reads API keys from Parameter Store,** as `read-acquire-tokens-from-parameter-store` specifies, because calls that fill a field now run there.
- **The three source-owned caches are removed** and what they hold is moved once, by a one-time script run against a clone of the workspace, as `~/dev/PoliceConductUS/intake-workspace/migration-2026-11-17/` was (owner's ruling, 2026-11-17, in place of AGENTS.md's rule that cache changes go through the CLI). CourtListener's calls are carried over from its `.api-calls.jsonl` call logs; the logs and `docket-cache.json` are deleted only after the move and the reset after it are verified.
- **Hand-review results (the design's "document review") are no longer produced.** Minnesota's existing reviewed analyses are moved into the cache as call entries that say who produced them, recording `gpt-6-astra`, the Codex default on the days they were made, as the model of each (owner's decision, 2026-11-18). An outcome the move writes carries `producedBy` and may leave out `startedAt` and `intakeVersion`. A moved request is the request today's code would make, as a lookup key, not a record of what was sent then.

## Capabilities

### New Capabilities

- `call-and-file-cache`: Call results as entries of the resolved-property cache, the rule for calling again, and files as records.
- `service-clients`: The shared clients that wrap the cache for each outside service.

### Modified Capabilities

- `mn-post-discipline-orders`: Order documents are stored by namespace, their text and analysis are cached call entries made in `data generate`, which fills the five order fields; a hand-reviewed result is no longer accepted as new input.
- `data-request-document`: The simplified format leaves out `BinaryFile` and `photo_id` in place of `PersonnelPhoto`.

## Impact

Affected intake sources: `com/courtlistener/www/api`, `com/site/my/mnitservices/post-license-search`, `org/policeconduct/manual` (it handles `Personnel` updates and `BinaryFile` records and loses `PersonnelPhoto`), and the `photo` command (`src/cli/photo/`). Affected shared code: the resolved-property store and its envelope (`src/cli/state/resolved-property/`), the shared clients and `src/cli/service-clients.ts`, the `intake cache` command (`src/cli/cache/`), the import's resolver backend and agency graph, the acquire dependencies (`src/cli/acquire/`), the `data generate`, `data update` and `data reset` commands, the entity descriptors (`scripts/lib/entity-spec-generator.ts`), and `mise.toml`. Removed: `src/shared/io/CallResult.ts`, `src/shared/io/BinaryFile.ts` and `src/cli/state/call-cache/`.

Supabase: one migration that creates `binary_file`, adds `personnel.photo_id`, carries over the existing photo row and drops `personnel_photo`. This needs a generated type refresh: the entity descriptors gain `BinaryFile` and `Personnel.photo_id`, and `npm run generate:envelope-types` and `npm run generate:data-request-doc` are run.

Downstream: policeconduct.org reads `personnel_photo` to stage photos into its build; it changes to read `binary_file` and its `workspace_path`, so that the next website build after the migration works (owner's ruling, 2026-11-19: no release order).

Order of work: (1) this change's code, including the rework onto one cache and the personnel photo task; (2) the CourtListener and photo part of the one-time move; (3) `keep-state-under-one-root`'s one-time move, which removes `assets/` once the photo is moved, and then its code; (4) the full CourtListener acquire; (5) the Minnesota task and the Minnesota part of the move; (6) `data reset --no-acquire`, so that every source is rebuilt from the cache, and then the deletion of the old files. Minnesota POST is started only after CourtListener is fully implemented and the owner says to; it must be finished before the next reset. After the reset the workspace is synced to S3 by the policeconduct.org command that runs after `data generate`; that command is not part of this change.

The design is in [design.md](design.md) and is recorded in ADR 0039, proposed with this change and to be brought in line with it (tasks).
