# Design: every acquire gets its answers through the cache

Related documents: [proposal](proposal.md), [tasks](tasks.md), [Census and acquire spec changes](specs/config-driven-source-import/spec.md), [acquire.yaml spec changes](specs/workspace-state-layout/spec.md), [cache spec changes](specs/call-and-file-cache/spec.md), [Oregon spec changes](specs/oregon-dpsst/spec.md), [Minnesota spec changes](specs/mn-post-discipline-coverage/spec.md), [stage completion spec changes](specs/intake-stage-completion/spec.md), [service clients spec changes](specs/service-clients/spec.md). The design this change depends on is [`cache-call-results-and-files`](../cache-call-results-and-files/design.md) ([ADR 0039](../../../docs/adr/0039-the-cache-holds-call-results-and-files.md)). It also follows [`keep-state-under-one-root`](../keep-state-under-one-root/design.md), whose code lands first.

## Problem statement

`data acquire` keeps two ways to carry work from one acquire to the next:

- **`resume`** in `state/<namespace>/acquire.yaml`. An acquire writes it when it starts, pointing at its own output folder, and removes it when it completes. The next `data acquire` of the namespace copies that folder into its own output (`src/cli/acquire/index.ts`). `data acquire --from-local` (`src/cli/acquire/acquire-from-local.ts`) writes `resume` too, but copies only the staged files.
- **`previousSourceDirs`** in `AcquireDeps` (`src/cli/transform/source-transform.ts`), read only by the Census Gazetteer acquire. Today it holds the `resume` and `latest` folders. Once `keep-state-under-one-root`'s code lands, it holds the `resume` folder and the last entry of the `acquires` list, which replaces `latest`.

The owner ruled on 2026-11-18 that both are removed once every call result and downloaded file an acquire makes goes through the cache. The owner also ruled that day that `cache-call-results-and-files` and `keep-state-under-one-root` keep `resume` and `previousSourceDirs`, and that this change, `cache-every-acquire`, moves the remaining acquires onto the cache and then removes both. `cache-call-results-and-files` puts CourtListener on the cache. Four acquires still make their calls outside the cache and find earlier work only in their own output folder:

| Source                                                                         | How it fetches today                      | What it reuses from its output folder                                                                                                                                       |
| ------------------------------------------------------------------------------ | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gov/census/www2/gazetteer` (Census Gazetteer and TIGER files)                 | `fetch`                                   | ZIPs in its own and the `previousSourceDirs` folders, checked against the remote file by a range request                                                                    |
| `net/bpl-orsnapshot/www/public-inquiry-cj` (Oregon DPSST, the licensing board) | ASP.NET form posts, cookies, one session  | `manifest.json` and the search, employment, certificate and agency pages it lists                                                                                           |
| `com/site/my/mnitservices/post-license-search` (Minnesota POST Board)          | Aura Apex actions posted inside a browser | `agencies/agencies.csv`, `officers/*.roster.json`, `officers/*.detail.json`, `discipline-requests/*.json` (`.search.json`, `.resolution.json`, `.complete.json`), documents |
| `org/wikipedia/en/us-federal-law-enforcement-agencies`                         | `fetch`                                   | `federal-le.html`                                                                                                                                                           |

Its own output folder holds what `resume` copied in, and also what `--from-local` staged there: `--from-local` copies the staged files into the new output before it runs the acquire, so each of the four acquires uses a staged file of a name it reads.

## Goals

- Each of the four acquires makes every call and download through a shared client, so each answer is a `CallResult`, and each file a `BinaryFile`.
- Running an acquire again after an interruption calls only what the cache does not answer, and writes a complete output into its own command folder (the folder `data acquire` makes for the command; its output is `command/<folder>/<namespace>/output`).
- `resume` and `previousSourceDirs` are removed.
- The files each acquire writes into its command folder, and so the transforms, do not change, except two files no transform reads: Oregon's `session-form.html` and Minnesota's `discipline-requests/<license>.complete.json`.

## Non-goals

- The Minnesota order documents. `cache-call-results-and-files`' Minnesota task moves them onto the file download client and their text and analysis into `data generate`.
- The other acquires. Clearinghouse (`net/clearinghouse/api`) and PSV (`org/psvproject/arrest-tracker`) fetch outside the cache but reuse nothing from an earlier folder. YouTube keeps its progress in its own state. Irving reads local files. Submissions syncs with the `aws` CLI. The manual source writes only state. They need nothing from `resume`.
- The `acquires` list in `acquire.yaml`, which `keep-state-under-one-root` adds.
- The "acquire is due" warning. The owner ruled that it is ignored for now; it is not built (`cache-call-results-and-files`, open question 9).

## Terms

The terms of `cache-call-results-and-files` apply: cache, request, fingerprint, outcome, client, item failure, outage. Its call rule (its section 3) says when a call is made again: an outcome with no `retryAfter`, or one whose `retryAfter` is in the future, stands. In addition:

- **Stands**: an outcome stands when that call rule says not to call again.
- **Refresh interval**: the time after a successful outcome when the caller wants the call made again. The caller passes it to the client as `refreshAfterMs`, and the client records it as the outcome's `retryAfter`.
- **Session state**: anything a site hands out for one session and expects back: the ASP.NET `__VIEWSTATE`, `__VIEWSTATEGENERATOR` and `__EVENTVALIDATION` fields, cookies, the Aura `aura.context` and `aura.token`, Aura action IDs, and the `r` request counter. Aura is the Salesforce page framework; an Apex action is a server call it posts.
- **Host check**: the client's check of a download host before its first call that the cache does not answer (`cache-call-results-and-files`, section 4).
- **Attempt**: in this change, the function a caller gives the download client that makes one call to a site and sorts what came back into a file, a JSON response, an item failure or an outage (section 1). It is not the inherited sense of one try at a request; the client may run an attempt several times.
- **Answer check**: a source's check that one answer is usable, made inside the source's attempt (section 1). A check that needs another call's answer runs after the calls (section 6).
- **Skipped**: the client's result for a call it does not make because its service is down. It is not an entry of Minnesota's `skipped.yaml`.
- **Completion marker**: the `acquire-complete` file `data acquire` writes into a command folder when the acquire succeeds.

## Owner decisions (2026-11-18)

1. **Oregon:** one call result per unit (a search prefix or an officer), fetched whole in one session (section 3).
2. **Census:** a range request for each ZIP's tail on every acquire. The whole ZIP is requested with the tail's SHA-256 and the size (section 2).
3. **Refresh intervals:** 7 days for every successful answer of the four acquires. The exceptions are the Census tail requests, at 0 (made again on every acquire), and Census ZIPs, with none (kept until the tail or size changes) (section 8).
4. **Minnesota officer details:** one Aura request per officer, about 11,200 requests, with no batching across officers (section 4).
5. **Minnesota `agencies.yaml`:** it stays as the source's record of agency IDs, never re-derived. The `getAgencies` search for an agency it does not hold is a cached call (section 4).
6. **Oregon `session-form.html`:** no longer written (section 3).

The owner gave these decisions in the review session of 2026-11-18; this section is their record.

## Proposed architecture

### 1. The file download client takes the request and the attempt from its caller

`DownloadClient.download(url, { fetch, refreshAfterMs })` builds the request `{ service: "download", operation: "get", url }` (`downloadRequest` in `src/shared/services/download-client.ts`) and makes a `GET` through `httpGet`. That is enough when the URL alone decides the answer and one `GET` gets it. It is not enough for the four acquires, which post forms, ask for byte ranges and send Apex actions, often several to one URL, and some of whose answers take several requests or a browser.

`download` takes these options:

```ts
download(url: string, options?: {
  operation?: string;                   // default "get"
  parameters?: Record<string, unknown>; // what decides the answer, beyond the URL
  attempt?: () => Promise<CallAttempt>;
  expects?: "file" | "response";        // default "file"
  refreshAfterMs?: number;
}): Promise<DownloadResult>;

type DownloadResult =
  | ({ status: "succeeded"; cached: boolean; outcome: CallOutcome } &
      ({ kind: "file"; file: StoredBinaryFile } | { kind: "response"; response: unknown }))
  | { status: "failed"; error: ItemFailure; outcome: CallOutcome }
  | { status: "skipped"; service: string; retryAfter: string };
```

`CallAttempt` is the client base's existing type (`src/shared/services/client-base.ts`): a file, a JSON response, an item failure, or an outage. `cachedCall` already takes such a call with no arguments. The per-call `fetch` option goes; `attempt` replaces it, and its one test ("uses a caller's fetch for the check and the download") is rewritten. `cache-call-results-and-files`' design still describes its Minnesota task as downloading "with its browser fetch"; that task uses an attempt instead, and its design text is updated in that change (reported to its owner as a cross-change finding).

An answer is returned as the client stored it, fresh or cached, so a fully cached run writes the same files as the run that called. `expects` says how it is read, because a stored outcome does not say whether its file was served or is a JSON response over 256 KB: `"file"` returns the binary file; `"response"` returns the JSON, read inline or from its file (`jsonResponse` in the client base). An attempt whose answer is of the other kind has a defect (below); no caller needs an exception. A plain `get` expects a file, so its result is `kind: "file"` and `complaint-summary-resolvers.ts`, the client's one other caller, narrows on `kind`.

**The request.** It is `{ service: "download", operation, url, parameters }`. `downloadRequest(url, operation?, parameters?)` builds it. A request with no `parameters` leaves the key out, so the request of a plain `get` is the same as today and its fingerprint does not change. A test pins the fingerprint of `downloadRequest(url)` for one URL.

The caller puts in `parameters` only what decides the answer. Session state is never in a request. It is taken, inside the caller's attempt, from the session that makes the call. So the same request in a new session has the same fingerprint, and a request from an interrupted run is found by the next run. The request schema rejects a key named exactly like a secret (`cookie`, `token` and others, `src/shared/io/CallResult.ts`), but not `__VIEWSTATE`, `__EVENTVALIDATION`, `aura.context` or `aura.token`. The guard against session state is therefore a test in each source that builds its requests in two sessions with different session state and finds them equal. The client does not apply `parameters`; the attempt sends what they name (a `Range` header, a form body, an Apex action).

**The attempt.** Without one, the client makes its own `GET` of the URL, with its 60-second timeout, and sorts the answer as today (`httpFailure`). With one, the client calls it when the call rule says to call, and records what it returns. The attempt makes the call any way its source needs: a POST, a range request, a call from inside a browser page, or several requests that make up one answer. It sets its own timeouts. It returns:

- a **file** (bytes, content type, extension, HTTP status) for a page, a CSV or a ZIP the site served;
- a **response** for a JSON answer (an Aura response, an Oregon unit, a Census tail summary). The client base keeps a response of up to 256 KB inline in the call result. A larger one is kept as a file, which today needs an HTTP status for the file's origin, and an answer made of several requests or read from a browser has no one status; until open question 5 is answered, such an answer stops the command, as `client-base.ts` does today;
- an **item failure** when asking the same request again would give the same answer: a 4xx other than 429, a body longer than asked for, a ZIP whose tail does not hash to the `tailSha256` its request names (the file changed after the tail was asked; the next acquire's tail makes a new request), a page the parser rejects, an Aura action that did not succeed, or a record count that differs from the rows returned;
- an **outage** when there is no answer, or the answer may change if asked again: a 429 or 5xx, a connection error or timeout, a body cut short, a ZIP whose tail matches but whose CRCs do not verify (a damaged transfer), an Oregon page out of sequence or repeated (the site changed during the call), a bot challenge left unsolved, a session the site ends twice in one call, an Aura reply that is not JSON or asks the page to reload (Salesforce's `aura:clientOutOfSync` and `aura:invalidSession` events), an Aura network error.

Each source section says which of today's errors goes where. For a site reached through a session (Oregon, the Minnesota license search), a 401 or 403 is an outage: the site turned the session away, not the item. An attempt catches the errors of its own calls and returns them as one of these. An attempt that throws has a defect in intake, not in the site: this change's rule is that the client records nothing and the command fails, naming the call's operation and URL. The client records only the last try of an attempt as the call's outcome. Attempts use the global `fetch`, as the four acquires do today, so tests stub it as they do today; Census keeps its `fetchBytes` and `fetchRange` parameters. A browser that does not launch (a locked profile, a wrong `CHROME_EXECUTABLE_PATH`) is such a defect, so it is never recorded as an outage of the site.

So a source decides, with the knowledge only it has, whether a failure belongs to the item or to the site's state. The client still decides the rest: whether to call, the host check, the retries of an outage, the down mark, and the recording. An item failure is recorded with error kind `item` and the attempt's message, is not retried, does not mark the host down, and is returned to the caller; the host's other calls go on. How a standing item failure is called again is open question 1. An outage is retried up to 5 more times, waiting at most 60 seconds each time; each retry runs the whole attempt again (an Oregon unit from its first page), and then the host is marked down for the rest of the source's run. A rejected answer is not kept as the answer; whether its bytes are kept as evidence is open question 6.

The retries a source makes today inside one call (`retryTransientAuraAction` in Minnesota's `post-client.ts`) go: the attempt returns an outage, and the client retries.

**The host check** always uses the client's own `fetch` (a `GET` of the host's root, which any HTTP answer passes), never an attempt. Checked 2026-11-18 from Node: `https://mn.gov/` answers 200, `https://mnitservices.my.site.com/` 200, and `https://www.bpl-orsnapshot.net/` 403, each an HTTP answer; Census and Wikipedia are fetched with Node today. A host check that gets no answer stops the source's work at once, as `cache-call-results-and-files` requires; section 6 does not apply to it.

**The result.** A successful result says whether the answer came from the cache (`cached`: false when this command made the call, also for a caller that shared another caller's call in flight) and gives the file or the response. `cachedCall` reports which, so the client base changes for it. The caller writes the answer into its command folder.

### 2. Census Gazetteer (`gov/census/www2/gazetteer`)

| Call                                                                       | Request (`download`)                                                    | Answer                                          | Refresh interval |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------- | ---------------- |
| The Gazetteer page, the year's page, the TIGER index, each TIGER directory | `get`, the URL (no attempt)                                             | HTML file                                       | 7 days           |
| The hierarchy file (a file whose name does not end in `.zip`)              | `get`, the URL (no attempt)                                             | The file                                        | 7 days           |
| The tail of a ZIP                                                          | `get-tail`, the URL, `parameters: { range: "bytes=-65557" }`            | Response `{ size, tailSha256, identifiesFile }` | 0: every acquire |
| A whole ZIP                                                                | `get`, the URL, `parameters: { tailSha256, size }` from the tail answer | The ZIP                                         | None, or 0       |

The pages and listings come first, in today's order, and today's selection checks run between them on their answers: `selectPublishedGazetteerPage` and `discoverLatestGazetteerLinks` choose the next pages, then the year check and `assertPublishedSourceLinks`. Every ZIP depends on all of them. So the accepted requirement "Shared published Census vintage" stands: when a page or listing fails or is skipped, or a selection check fails, the acquire asks for no ZIP and fails at once, naming the URL and its status, the time to try again for a skip, or the check. A page that fails a check stands for 7 days, so a run again within that time fails the same way (open question 1).

How a ZIP is acquired. A ZIP ends with its central directory, which lists every entry with its CRC-32 and sizes, and an end record of 22 bytes plus a comment of up to 65,535 bytes; so its last 65,557 bytes hold the whole central directory of most files, and a change to any entry changes them.

1. **The tail.** It is asked with `expects: "response"`, and its refresh interval of 0 means it is never answered from the cache. Its attempt sends `Range: bytes=-65557`. On a 206 it requires a `Content-Range` whose range ends at the total size less one and a body of the range's length (a 206 that breaks these is an outage: the server answered the range badly this time, and today's code also tries it again on its next run), and answers with a response: the total `size`, the SHA-256 of the bytes the tail covered (`tailSha256`), and whether they hold the whole central directory (`identifiesFile`, from `containsCentralDirectory` in `acquire/download.ts`). The tail's bytes are not kept. On a 200 the server has ignored the range and sent the whole file: the attempt reads `size` and `tailSha256` from that body and answers with the same response, and step 2 asks for the whole ZIP. That costs a second download only from a server that ignores ranges; `www2.census.gov` sends `Accept-Ranges: bytes` (checked 2026-11-18). A ZIP smaller than 65,557 bytes comes back whole in its 206 and is also downloaded by step 2. The tail attempt has no timeout, as the whole-ZIP attempt.
2. **The whole ZIP.** Otherwise the acquire asks for it, naming `tailSha256` and `size`. If the remote file is unchanged since an earlier acquire, the request is the same and its outcome stands, so nothing is downloaded. If the remote file changed, its tail or size changed, so the request is new and the file is downloaded. The earlier file stays in the cache. The attempt is a plain `GET` with no timeout, as today. A body shorter than `size` is an outage (the transfer was cut), and so is a body of the right length whose tail matches but whose entries do not verify against their CRCs. A body longer than `size`, or one whose tail does not hash to `tailSha256`, is an item failure (section 1). The CRC check takes a buffer: `verifyZipContents(buffer)` in `src/cli/transform/parse/zip.ts` opens it with `yauzl.fromBuffer` and calls the existing `verifyOpenedZipContents`, as `verifyZipContentsFromFd` does for a file descriptor. Today a fresh download is checked only against a `Content-Length` header when one is sent, and only reused files for their CRCs; every download is now checked for both.
3. **A tail that does not identify the file.** When `identifiesFile` is false, the ZIP's download is asked with a refresh interval of 0, so it is downloaded on every acquire, as it is today.

The ZIP's file is written into the output under its URL's file name. The acquire logs, for each file, whether it came from the cache or was downloaded (`cached`).

What goes: `previousSourceDirs`, the search for candidates in earlier folders, `matchesRemoteZip`, and the deletion of ZIPs not in the selected set from the output. The output of `data acquire` starts empty (section 7), so it holds only the files the acquire writes; what an output staged with `--from-local` holds is open question 3. A cached ZIP whose bytes no longer hash to its name fails the read, naming the file, as every binary file read does. Today such a file is downloaded again. The cache treats it as damage to report, not to repair quietly; how it is repaired is open question 2.

The owner chose this over dropping the tail request and letting a refresh interval decide when a ZIP is downloaded again (decision 2). The tail request keeps the accepted behavior, in which the next acquire downloads a changed remote file. It costs one range request of 64 KB per ZIP on each acquire: 114 with today's links (3 Gazetteer files, 2 state and county TIGER files, 51 place, 51 county subdivision (COUSUB) and 7 consolidated city (CONCITY) files). Each tail request adds one outcome to its call result on every acquire, without end; its answer is never reused, and the outcomes are the record of what each acquire saw.

### 3. Oregon DPSST (`net/bpl-orsnapshot/www/public-inquiry-cj`)

The site is an ASP.NET WebForms application at `https://www.bpl-orsnapshot.net/PublicInquiry_CJ/` (`BASE_URL` in `parse.ts`). Each page after the first is a POST of the previous page's hidden fields (`postbackFields` in `parse.ts`) plus the `__EVENTTARGET` of the next page link. The view state therefore chains the pages of one search or one officer together inside one session.

**One call per unit.** A unit is one search prefix, one officer, or one agency page. The cache key names the unit and never the view state. URLs are under `BASE_URL`:

| Unit           | Request (`download`)                                                                                         | Answer                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| A search       | `search`, `EmployeeSearch.aspx`, `parameters: { name: <prefix> }`                                            | Response `{ form: string, pages: string[] }`, each page the HTML received |
| An officer     | `officer-pages`, the officer's `EmployeeDetails.aspx?RecID=…&RecNum=…&AgcyID=…`, `parameters: { officerId }` | Response `{ employment: string[], certificates: string[] }`, the same way |
| An agency page | `get`, `AgencyList.aspx?Agcy=<code>`                                                                         | HTML file                                                                 |

The officer's URL is the `EmployeeDetails.aspx` link of the officer's last affiliation row in search order, the row today's code keeps (`acquire.ts`). Search answers stand for 7 days, so within that time the same row is chosen. When a refreshed search orders the rows differently, the request is another URL, which is a new call, never another officer's answer. The request also names the officer ID, and the acquire parses each officer answer, fresh or cached, with the page parsers, which check the officer ID (`verifyOfficer` in `parse.ts`) before it writes `officer-<id>-*.html`. Whether `RecID` and `RecNum` stay the same across sessions is not known: the dev workspace's two full Oregon outputs hold the same files, copied by `resume`. If they change, they are session state and may not be in the request. So before Oregon is built, one prefix is fetched in two live sessions and its links compared (tasks 1.4). If they differ, the officer request is `officer-pages`, `EmployeeDetails.aspx`, `parameters: { officerId }`, and the attempt follows the link from the current search answer.

**`client.ts` changes.** `createClient` keeps its cookie jar, its `redirect: "manual"`, its 250 ms spacing and its 45-second timeout per request, but its `RequestHtml` becomes `(url, body?) => Promise<{ status: number; location?: string; html: string }>`: it returns each answer instead of throwing on a status that is not 2xx, and no longer renews a session and repeats the request by itself. It gains `openSession()`, which gets and validates the search form, and `hasSession()`. `createClient` returns `{ request, openSession, hasSession }`. `acquireOregon` takes `{ sourceDir, prefixes, download, client, log }`, where `download` is the file download client, `client` the session client and `prefixes` today's list (`OREGON_DPSST_PREFIXES`, A to Z by default). The attempts log a renewal, as `onSessionRenewal` does today. `parse.ts` throws a typed error for each check below, so an attempt sorts by type, not by message. The attempts decide:

- **A search or officer unit.** The attempt opens a session if none is open. A search unit then gets the search form (its answer's `form`, written as `search-<prefix>-form.html`; when the attempt had to open the session, the form it got doing so is this form, so it is not asked twice), posts the prefix and follows each next-page postback; an officer unit gets the employment page, follows its pages, posts the tab switch to the certificates tab (`mnuButtons`) and follows those pages, as `acquireOregon` does today for that unit. When the site redirects to its public `Logout.aspx`, the attempt opens a new session and starts the unit again from its first page, once; a second such redirect in the same attempt is an outage. Any other redirect is an outage. So the client may run a unit up to 6 times before it marks the host down. A page answered 401 or 403, 429 or 5xx is an outage, and any other 4xx an item failure. Today's errors sort this way: "Pagination gap" and a repeated page are outages (the site changed during the call); "Unsupported pagination command", an empty paginated page, "Missing ASP.NET viewstate" and any other parser rejection are item failures. A page without a next-page link ends the unit. So every page of a unit that is kept comes from one session (decision 1), and a unit is never answered half from the cache and half from a new session.
- **An agency page.** It is one `GET`, in the session. On a redirect to `Logout.aspx` the attempt opens a new session and asks again, once, as the accepted scenario "Public session expires" says; the request has no view state, so asking again in a new session is the same request. A second redirect is an outage, and a 404 an item failure. A 2xx page is kept. `parseAgency` needs the name expected from the affiliations, which is not in the request, so it runs after the call, on the kept page, as it runs today after each agency fetch. A page it rejects (an identity mismatch, missing address fields, an unrecognized email) is a failed check after the calls (section 6); the page stands for 7 days, so a run again within that time fails the same way (open question 1). The checks for conflicting affiliations and conflicting agency names also run after the calls, on the answers, as section 6 says.

The cookie jar lives for the command. The client makes one call per host at a time (`cache-call-results-and-files`, section 4), so two units never use the jar at once. The first call that needs a session opens one by getting the search form, inside that call's attempt.

**What the acquire writes.** It writes the files it writes today, under today's names, from the answers, as each answer comes: `search-<prefix>-form.html`, `search-<prefix>-<n>.html`, `officer-<id>-employment-<n>.html`, `officer-<id>-certificates-<n>.html` and `agency-<code>.html`. When every unit has an answer and the checks after the calls pass, it writes `manifest.json` with `complete` true, listing the numbered search pages, the officer pages and the agency pages as today (never the form pages, which the transform does not read). An acquire that fails writes no `manifest.json`, and the completion marker is missing too. The accepted requirement "Use the shared intake boundary" says the source preserves all original responses, so until open question 6 is answered, an attempt that rejects a unit writes the pages it received into the output before it returns the item failure, as today's code writes each page before it parses it. It does not write `session-form.html`, the form page that started the session. That page is not the answer to any request, and no code reads it (decision 6). Writing the form page of the first session opened in a run was turned down: its content would depend on which unit needed a session first.

What goes: `previousManifest`, `completedPages` and the checks of a saved manifest's identities and prefix scope. A run with a different prefix list is a different set of search units. The prefixes it shares with an earlier run are taken from the cache.

The owner chose one call result per unit over one per page (decision 1). Per page, the next page's postback would take the hidden fields of the cached previous page, so the pages of one search could come from runs days apart. Rows that moved between pages in that time would then be missed without an error. Per unit, a unit cut off partway is fetched again from its first page, as `resume` does today.

### 4. Minnesota POST (`com/site/my/mnitservices/post-license-search`)

The site is a Salesforce Experience site. Today the acquire opens a persistent Chromium profile (`state/.../browser-profile`) and, through `createPostLicenseSearchClient`, posts Aura Apex actions from inside the page with `page.evaluate(fetch)`. Each call carries the page's `aura.context`, a running action ID and a running request counter. The statistics page on `mn.gov` is behind a bot challenge and loads only in the browser (`agency-csv.ts`).

| Call                 | Request (`download`)                                                                                                     | Answer                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------- |
| The statistics page  | `get`, `https://mn.gov/post/boardscommittees/reportsstatistics/statistics/`                                              | HTML file                 |
| The agency CSV       | `get`, the CSV URL `findAgencyCsvUrl` reads from that page                                                               | CSV file                  |
| An agency search     | `post`, the Aura URL, one `getAgencies` action                                                                           | Response: the Aura answer |
| An agency roster     | `post`, the Aura URL, one `getLicensesByAgency` action                                                                   | Response: the Aura answer |
| A license search     | `post`, the Aura URL, one `getLicensesByLicense` action                                                                  | Response: the Aura answer |
| An officer's details | `post`, the Aura URL, the four actions of `officerDetailSpecs` for one officer license (its `contactId` and `licenseId`) | Response: the Aura answer |
| An order document    | As `cache-call-results-and-files`' Minnesota task defines it                                                             | PDF file                  |

The Aura URL in a request is `https://mnitservices.my.site.com/POSTLicenseSearch/s/sfsites/aura?aura.ApexAction.execute=1`, without the `r` counter. Each action in `parameters.actions` is the action's `params` object as `post-client.ts` sends it today: `{ namespace: "", classname, method, params, cacheable, isContinuation: false }`. Its `params` are the Apex parameters as sent (`agency`, `agencyId`, `licenseParm`, `contactId`, `licensePOId`, `maxThreshold`, `hasBeenDisciplined`). The action's `id`, `descriptor` and `callingDescriptor`, and the `aura.context` and `aura.token`, are not in the request.

The attempt numbers the actions of one request `1;a`, `2;a`, and so on, instead of using a running counter, so the stored answer parses the same way on every run, with `parseApexActions` matching by ID. Each Aura call times out after 60 seconds. Today's errors sort this way. Outages: a network error that `isTransientAuraError` matches today (`Failed to fetch`, `ERR_NETWORK`, `ERR_CONNECTION`, `Timeout`); Playwright's "Execution context was destroyed"; an Aura reply that is not JSON or carries `aura:clientOutOfSync` or `aura:invalidSession`; an Aura page that does not show an Aura context within 60 seconds ("did not expose an Aura context"). On `aura:clientOutOfSync`, `aura:invalidSession` or a destroyed context, the attempt closes the Aura page, opens it again, waits for a new Aura context and asks once more before it returns the outage, as Oregon renews its session. An Aura answer with a status that is not 2xx is sorted by status, as in section 1, with 401 and 403 as outages. The attempt sets `httpStatus` from the in-page fetch's status, so an answer over 256 KB can be kept as a file. Item failures: an action that did not succeed for another reason, and a `recordCount` that differs from the rows returned (`assertCompleteResultCount`, on the agency search, roster and license search as today). The stored answer is the Aura reply parsed as JSON, which `parseApexActions` reads. A roster over `maxThreshold` (2000) fails its count on every run, as today.

**The statistics page and the CSV.** Both are fetched in the browser. A single call keyed by the statistics page URL, whose attempt makes today's one visit and returns `{ csvUrl, csv }`, would save a visit and a CAPTCHA wait; open question 8 includes it. The statistics page's attempt opens it and waits for the CAPTCHA as `fetchPostAgencyCsv` does today; a page that is still a bot challenge when the wait ends is an outage. The CSV attempt also opens that page in the browser, and waits for and sorts a CAPTCHA there the same way, whether or not the statistics page answer came from the cache. The CSV request names the URL `findAgencyCsvUrl` reads from the statistics page answer. Its attempt opens the statistics page in the browser and clicks the link to that URL, because the site flags a direct request; when the live page has no link to that URL, it is an item failure naming the URL. A bot challenge in place of the CSV, or no CSV within 60 seconds of the click ("Timed out downloading"), is an outage; a CSV response that is not 2xx is sorted by status. The statistics page answer is the rendered page (`page.content()`), which `findAgencyCsvUrl` reads today, with the status of the navigation's response. The CSV answer is the body of the response the click triggers, with its status; when the site sends it as a download, which has no status, open question 5 applies. An unsolved CAPTCHA is retried by the client like any outage, each try waiting up to `MN_POST_CAPTCHA_WAIT_MS`; open question 8 asks whether a person should be in this loop at all. `agencies/citation.json` is written as today (`source`, `label`, the statistics page URL and the CSV URL), whether the answers came from the cache or not.

### 6. A failed or skipped call

Each of the four acquires needs every answer to produce a complete output. The accepted Oregon requirement already says it SHALL NOT claim a complete acquisition after a failure. So, for all four:

- An item failure or a "skipped" result for a call the output needs is collected, and the acquire makes its other calls that do not depend on that answer. When a host is down, the client skips the rest of that host's calls that the cache does not answer, at once, so this costs nothing. A call that depends on a missing answer (a Census ZIP whose listing failed, an Oregon officer whose search failed) is not made.
- A call the output needs is every call of sections 2 to 5, except a Minnesota order document the site no longer serves, which `cache-call-results-and-files` reports as no longer served. An agency the Minnesota site search does not resolve stays an entry of `skipped.yaml`, as today.
- A check that needs the answers of other calls runs once those answers are in: Oregon's `parseAgency` with the expected name, and its conflicting-affiliation and conflicting-agency-name checks, after the calls; Census's selection checks between its pages (section 2), where a failure ends the acquire at once because every later call depends on it. A failed Oregon check is collected with the failures, named by its check and the answer it read, and makes no call that depends on it. The answer stays in the cache as it stands.
- At the end, the acquire throws. The message names each item failure by its operation, its URL and the parameter that tells it apart (a prefix, an officer URL, an agency name, a license, a `contactId`), with the failure's message. It names skipped calls by the client's skip lines (`formatServiceSkips`: the service, when it went down, how many calls were skipped, the time to try again), not one by one, since a host that goes down early can skip thousands; Census also names the URL of a skipped page or listing, as the accepted "Fetch failure" scenario says. The four sources build this message with one helper, `acquireFailure({ failures, skips, skippedUrls }): Error` in `src/cli/acquire/acquire-failure.ts`, which the source throws. `failures` is a list of `{ call: string; message: string }`, where `call` is `"<operation> <url> <name>=<value>"` (for example `search https://www.bpl-orsnapshot.net/PublicInquiry_CJ/EmployeeSearch.aspx name=S`) or, for a check, the check's name and the file it read; `skips` is `deps.clients.download.skips()`; `skippedUrls` is the URLs a source must name one by one (the Census pages). The message is one line per failure, then one per skipped URL, then the skip lines. `data acquire` prints the skip lines only for an acquire that succeeds, so the message carries them. `data acquire` then does not record the acquire as completed.
- Running it again takes every answer that stands from the cache. It calls again only for a call with no outcome, or one whose `retryAfter` has passed.

A host check that gets no answer is not such a call: it stops the source at once (section 1).

An item failure has no `retryAfter`, so it stands until its request changes. A site that is fixed does not change the request, so an acquire that hits an item failure fails on every later run, without asking the site again. Today's code asks again on every run. This is open question 1, and this change waits for its answer.

### 7. Removing `resume` and `previousSourceDirs`

This step comes after `keep-state-under-one-root`'s code. By then `acquire.yaml` holds `acquires` and, while an acquire runs or after one fails, `resume`; `readCommandPointer` fails on any other key; `previousSourceDirs` holds the `resume` folder and the list's last entry; `data reset` no longer writes `acquire.yaml`; and `intake workspace migrate-state`, which copied `resume` between workspaces, is removed. Once the four sources are on the cache:

- `src/cli/acquire/index.ts`: no `resume` is written when an acquire starts, no earlier folder is copied into the new output, and no `previousSourceDirs` is passed. The "resuming the previous acquire" message goes. A new output starts empty.
- `src/cli/acquire/acquire-from-local.ts`: no `resume` is written and no `previousSourceDirs` is passed.

No workspace in `~/dev/PoliceConductUS/intake-workspace/` holds one once the `cache-call-results-and-files` move has deleted CourtListener's (checked 2026-11-18).

After this step no file under `src/` or `sources/` names `previousSourceDirs` or writes `resume` to an `acquire.yaml`, and no test does except the one that checks that such a file fails; test fixtures that write `resume` (`test/cli/data/reset.test.ts`) are changed with it.

An acquire that fails leaves its command folder as it is, without the completion marker, and nothing points at it. Its answers are in the cache.

### 8. Refresh intervals

An acquire is run to get current data, so its successful answers need a refresh interval. Without one, an outcome stands for good and a later acquire returns the same answer forever. The interval is also how long an interrupted acquire can wait before it is run again and still reuse every answer it got.

The owner set the intervals (decision 3):

- 7 days for every successful answer of the four acquires, except the order documents (section 4). An acquire run again within a week reuses everything.
- 0 for the Census tail requests, which are made again on every acquire.
- None for Census ZIPs. A ZIP is kept until its tail or size changes, which changes its request.
- 0 for a Census ZIP whose tail does not identify it (section 2, step 3). This follows from decision 2: such a ZIP has no tail that identifies it, so it is downloaded on every acquire, as today.

## Open questions

1. **A standing item failure.** Under the call rule an item failure stands until its request changes, and nothing is invalidated by hand, so one item failure (a 404, a 403, a failed answer check) fails its acquire on every later run, even after the site is fixed. Answers of different ages can also disagree (an interrupted Oregon run reuses search units up to 7 days older than the ones it fetches), and nothing lets the operator ask again before they expire. This is `cache-call-results-and-files`' open question 3 ("how a standing item failure can be called again"). Options: (a) an item failure of an acquire call gets a `retryAfter`, as an outage does; (b) a CLI operation, with `--message`, calls a named request, or a source's acquire calls, again; (c) accept it until that question is decided. Recommendation: (a) and (b), decided in `cache-call-results-and-files` before this change starts.
2. **A damaged cached file.** A cached ZIP whose bytes no longer hash to its name fails every later acquire, and AGENTS.md forbids editing cache files outside the CLI. Options: (a) `cache-call-results-and-files` adds a CLI operation that removes a damaged file with its call result, with a `--message`; (b) the operator restores the file from a backup; (c) the download client downloads a damaged file again. Option (c) repairs quietly, which this design rejects. Recommendation: (a).
3. **Files staged with `--from-local`.** Today each of the four acquires uses a staged file of a name it reads: a ZIP, Oregon's pages and `manifest.json`, Minnesota's `agencies.csv` and other files, `federal-le.html`. Once they read nothing from their output, the acquire writes over such a file, and only the Minnesota workbooks still have a use. Options: (a) an acquire fails, naming the file, when its output already holds a file it would write; (b) `acquireFromLocal` accepts only the inputs a source reads (today the Minnesota workbooks) and refuses `--from-local` for a source whose acquire reads none, in one place; (c) a staged file is used as the answer to its call, which puts a file in the cache that no call answered. Recommendation: (b).
4. **Where "fail at the end" lives.** Section 6 has each of the four acquires collect its failed and skipped calls and throw. `acquireSource` already collects the clients' skips and records the acquire as completed anyway; `cache-call-results-and-files`' open question 5 asks whether every acquire with skipped calls fails. Options: (a) `acquireSource` and `acquireFromLocal` fail, and do not record completion, for any acquire with skipped calls, and each source throws for the item failures it cannot use; (b) only the four acquires fail, as section 6 says. Recommendation: (a), which also answers that open question for CourtListener; the specs then state the rule for every acquire.
5. **An answer kept as a file that no URL served, or with no status.** A JSON response over 256 KB is kept as a file whose `download` origin needs a URL and an HTTP status. An Oregon search unit (many pages, each with its view state) is routinely over 256 KB and is made of many requests; the Minnesota CSV can arrive as a browser download with no status. Until this is answered, such an answer stops the command, so Oregon cannot start. This is `cache-call-results-and-files`' open question 6. Options: (a) an origin for an answer made by an attempt (`{ kind: attempt, url }`, no status); (b) an Oregon unit keeps each page as its own binary file, with its own URL and status, and its response lists their SHA-256s, which needs a `CallAttempt` that hands the client several files; (c) an attempt reports the status of its last request. Option (c) makes up a status. Recommendation: (a), decided in `cache-call-results-and-files`.
6. **The bytes of a rejected answer.** `cache-call-results-and-files` keeps a file that later fails a caller's check in the cache as the evidence of what was served. An answer an attempt rejects (a ZIP whose CRCs fail, an Oregon page the parser rejects) is not kept as the answer, and a failed outcome names no file (`CallResult.ts`). Options: (a) a failed outcome may name the rejected file, so the evidence is kept and findable (a `CallResult` schema change in `cache-call-results-and-files`); (b) the acquire writes the rejected bytes into its command folder only; (c) answers are kept as successes and checked after the call, so a bad answer stands for its refresh interval. Recommendation: (a).
7. **Census, Oregon and Wikipedia wait for Minnesota.** The sources and the removal land together, and Minnesota waits for a dependency task with no design. Options: (a) wait, as the order of work says; (b) land Census, Oregon and Wikipedia with the end of the copy-in of `resume` now, so an interrupted Minnesota acquire starts again from nothing until Minnesota moves; (c) fold Minnesota's Aura and statistics-page work into `cache-call-results-and-files`' Minnesota task, so its fetch layer is designed once; (d) split this change: the client options; Census and Wikipedia with the removal of `previousSourceDirs`, keeping Census's deletion of unselected ZIPs until `resume` goes (the Oregon transform reads only what `manifest.json` lists, and no transform reads `.complete.json`, so only Census needs it); Oregon after open question 5; `resume` last. Recommendation: (c) with (d).
8. **A person solving the Minnesota CAPTCHA.** The statistics page and the CSV wait up to `MN_POST_CAPTCHA_WAIT_MS` for a person to solve a CAPTCHA, as today, and the license search page can show one too (`post-client.ts`). With `MN_POST_CAPTCHA_WAIT_MS=0` an unsolved CAPTCHA is an outage at once. The owner ruled that the company has no manual steps in a pipeline. As an outage, an unsolved CAPTCHA is retried up to 5 more times (up to about 18 minutes at the default wait) and then marks `mn.gov` down for an hour. Options: (a) keep it as designed; (b) an unsolved CAPTCHA is an outage that is not retried within the command; (c) the acquire gets the agency CSV without a person, or without the statistics page. Recommendation: (c) as a follow-up, (b) meanwhile, and the single statistics-page-and-CSV call of section 4.
9. **How large the cache grows.** Each refresh of an Oregon unit or a Minnesota detail stores a full copy, because Oregon pages differ by view state each session and an inline response is not shared between outcomes. The dev workspace's last full outputs give the size of one refresh: Oregon 1.5 GB in 45,221 files (2026-10-06), Minnesota's `officers/` 617 MB in 11,601 files (2026-10-18). An acquire of both each week would add about 2 GB a week, about 110 GB a year, and the command folders hold the same pages again. Each call result also grows by one outcome per refresh, and every lookup reads and rewrites the whole envelope (`readCallResult`, `appendOutcome`), so the time of a lookup grows with it. `cache-call-results-and-files` deletes nothing from the cache (its non-goal). Options: (a) a retention rule in `cache-call-results-and-files` (for example, keep the outcomes of the last N acquires of a request); (b) a longer refresh interval for these two sources; (c) accept it and watch the cache size report. Recommendation: (a), decided before the first weekly acquire.
10. **The service name of an attempt's call.** Every call of this change is `service: "download"`, which is part of the fingerprint, though many are form posts and Apex actions. Renaming it later misses every entry written under it. Options: (a) keep `download` and say the client is the per-host HTTP client; (b) give calls made by an attempt their own service name, on the same per-host base. Recommendation: decide before the first entries are written; (a) is the smaller change.
11. **Which answers an output took from the cache.** A new acquire's output can be made wholly of answers other commands fetched up to 7 days earlier, and nothing in the output says which, or when (only Census logs it). Options: (a) the output gains a file listing, for each file, the request fingerprint and the outcome's `commandId` and `completedAt`; (b) the call results are the record, and nothing is added. Recommendation: (a), which a fully cached run writes the same way.
12. **The refresh interval and an interrupted acquire.** Decision 3's 7 days serve two needs: finishing an interrupted acquire, and reusing answers across completed ones. So an acquire run within a week of another records a new acquire with no new data, and answers of different ages mix (section 3). Option: an answer stands for an acquire only if it was recorded after the namespace's last completed acquire started (the `acquires` list gives that time), with 7 days as an upper limit, a cutoff `standingOutcome` reads as it reads `keepSucceeded`. Recommendation: put it to the owner as a change to decision 3.

## Alternatives considered

- **Keep `resume`, and cache only the downloads.** Rejected by the owner's ruling. It would keep two ways to reuse work, and `resume` copies a whole earlier folder forward, stale files included (section 7, and the interim problem in the order of work), where the cache returns only the answers a new acquire asks for.
- **Carry the files of earlier outputs into the cache once.** Rejected: a moved file has no download call result, so no request finds it. The owner ruled for `cache-call-results-and-files` that no HTTP details are made up for a moved file. The first acquire after this change downloads once.
- **A client per site in `src/shared/services/`.** Rejected: it puts source-specific code in shared code. The download client with the request and attempt supplied by its caller serves all four.
- **Let each source call the client base itself.** Rejected by `cache-call-results-and-files` (its failure 4: the same logic written several times). Each source would also keep its own map of hosts and its own host check.
- **Keep the caller's `fetch` and an answer check.** Rejected: a `typeof fetch` that stands for several requests or a browser call has to make up a `Response` and a status no server sent, and every failed answer check would be one sort of failure, where a bot challenge is the site's state and a bad CRC is the item's.
- **Key an Oregon page by its view state.** Rejected: the view state changes with every session, so no later run would find the entry.
- **HTTP conditional requests for Census ZIPs** (`ETag`, `Last-Modified`). Checked 2026-11-18 on `https://www2.census.gov/geo/tiger/TIGER2024/STATE/tl_2024_us_state.zip`: the server sends `Last-Modified` and `Content-Length` but no `ETag`. A date is the server's statement about a file, not its bytes; the tail identifies a ZIP by its own central directory and size, which today's code already reads. The owner chose the tail request (decision 2).
- **Reuse only answers newer than the last completed acquire.** Not taken, because decision 3 sets 7 days; open question 12 puts it back to the owner.
- Choices made inside the sections: dropping the Census tail request for a refresh interval (section 2, decision 2); writing the first session's form page (section 3, decision 6); one Oregon call result per page (section 3, decision 1); batching Minnesota officer details (section 4, decision 4); replacing `agencies.yaml` with cached searches (section 4, decision 5).

## Notes on the specs

The specs in this change follow the owner's decisions.

The modified Census, Oregon and stage completion requirements keep the names of the accepted scenarios "Completed acquisition already has matching files", "Changed or damaged file", "Interrupted acquisition from a different vintage", "Resume interrupted statewide acquisition" and "Locally seeded analysis fails", with new content: `openspec validate` refuses a MODIFIED requirement that drops a scenario the accepted spec has. "Changed or damaged file" now holds the changed file; the damaged one has its own scenario. The accepted Minnesota scenario "a resumed acquire re-does nothing already on disk" has no delta here, because `cache-call-results-and-files` removes the requirement that holds it.

The `workspace-state-layout` delta modifies a requirement `keep-state-under-one-root` adds, and the `service-clients` and `call-and-file-cache` deltas modify requirements `cache-call-results-and-files` adds. Archive refuses a MODIFIED delta whose spec does not exist yet, so those two changes are archived first.
