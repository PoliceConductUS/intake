## Why

State is kept under three roots in the workspace, and the documents name a fourth layout. The code writes a source's own state to `state/<source id>/`, the source-name mapping, `ResolvedProperty`, `PropertyCorrection`, `CallResult` and `BinaryFile` records to `state/intake/namespaces/<namespace>/`, and records requests and initial agency roots to `intake/state/namespaces/<namespace>/`. AGENTS.md, ADR 0010 and the `artifacts-database-import` spec say `intake/state/namespaces/<namespace>/` for all of it. The dev workspace has no `intake/` folder at its root. The owner's rule (2026-11-17): the workspace has one state root, `state/`; `state/<namespace>/` holds the state a namespace owns, and the root intake module is a namespace like any other.

## What Changes

- The workspace layout is three folders at the top: `command/`, `state/` and `data/`. No command checks the top of the workspace (owner's decision, 2026-11-18); the one-time move puts what it has rules for into this layout and leaves anything else where it is.
- `data/mutations/` stays where it is: it is the current set of data mutations that `intake data up` applies, and it belongs to no namespace.
- `assets/` and `media/` are no longer used. A binary file is added to the cache and attached to the property that uses it, as `cache-call-results-and-files` defines.
  - `assets/PersonnelPhoto/` belongs to `cache-call-results-and-files`: that change alone moves the photo into the cache and sets the person's `photo_id`. This change only removes the `assets/` folder once that move has run and the photo is in the cache with the same SHA-256.
  - `media/` is moved by this change's one-time move. In the dev workspace it holds five files in `media/farmakes-voicemail/` (`original.mp3`, `farmakes-voicemail.mp4`, `title-card.png`, `provenance.json`, `youtube-metadata.json`), which no record names. Each becomes a `BinaryFile` under the namespace `org/policeconduct/manual` (owner's decision, 2026-11-18), with its SHA-256 unchanged and origin `local` (its file name and the time of the move), and the move lists it as used by no record. `provenance.json` is moved with the others, so its record of the source URL is kept.
- `gov/` goes under `state/`. In the dev workspace its only files are in `gov/irvingtx/arrests/source/`; the move puts them at `state/gov/irvingtx/arrests/source/`, which does not exist yet. They are already the evidence of a completed Irving acquire: `arrests.xlsx` and every file in `geography/` are byte-identical to `command/2026-10-26T04-25-42-484Z-icypgxzfk0lnu02mla8qul7t/gov/irvingtx/arrests/output/evidence/`. (`arrests-normalized.jsonl` in that folder differs from the one that acquire wrote, and no code reads it.)
- Every namespace supports any number of acquires, not one. Each acquire is a command, and its output is in its command folder. A phase finds a namespace's input by reading the command folders, keeping the acquire commands of that namespace that completed, and processing them in one fixed order: the order in which the data was acquired, that is, the time each acquire ran, whatever order the commands that read it run in (owner's rule, 2026-11-17). A command folder's name starts with the time its acquire started, so that name gives the order; no date of the data itself is needed. What the code does today:
  - `retainedAcquiredInputs` in `src/cli/data/acquired-inputs.ts` lists every `command/<folder>/<namespace>/output` that has its completion marker and one `Command` envelope whose arguments are `acquire <namespace>` or `data acquire <namespace>` (an acquire `--from-local` included), sorted by the command folder's name, which starts with the time the acquire command started.
  - Only `data reset` uses it (`src/cli/data/reset.ts`). For each completed acquire in that order it points `latest` in `state/<namespace>/acquire.yaml` at that acquire and runs `data transform`, `data generate` and `data up`, then puts the pointer back. The outputs combine through the database: each acquire is transformed, generated and applied alone, earliest first. A record that a later acquire also holds is compared with what is there and updated; a record that only an earlier acquire holds stays as that acquire wrote it, because a generated mutation only creates or updates.
  - `data transform` and `data generate` run alone read one acquire, the `latest` of `state/<namespace>/acquire.yaml` (`sourceInputDir` in `src/cli/transform/index.ts`). When two acquires complete between transforms, the earlier one is processed only by the next reset. This change makes every phase that reads acquired input find it through `retainedAcquiredInputs`.
  - `data transform` and `data generate` run alone replay every completed acquire not yet processed, in order, oldest first, before the latest, as `data reset` does: each through `data transform`, `data generate` and `data up` (owner's decision, 2026-11-18). What the code records today does not tell which acquires were processed: `state/<namespace>/transform-completion.json` (`src/cli/state/transform-completion.ts`) holds only the last input folder transformed, with its digest, and is overwritten each time, and nothing records which acquires a generate included.
  - `state/<namespace>/acquire.yaml` stays the standard place for a namespace's acquire input (owner's decision, 2026-11-18). Today it holds only `latest` and `resume`, read and written by `readCommandPointer` and `writeCommandPointer` in `src/cli/state/command-pointer.ts`; it has no `apiVersion` or `kind`, so it is not an envelope. It becomes the ordered list of every successful acquire run, which later phases read to choose their inputs: every listed acquire not already in the targeted database, oldest first (owner's decision, 2026-11-18). It holds nothing about which acquires were processed.
  - `latest` is replaced by the list's last entry. Every reader of `latest` today uses it as "the last successful acquire": the acquire itself, which passes it to the source as one of `previousSourceDirs` (`src/cli/acquire/index.ts`, `src/cli/acquire/acquire-from-local.ts`; the Census gazetteer acquire uses those folders); `sourceInputDir` (`src/cli/transform/index.ts`); `sourceHasAcquiredInput` (`src/cli/data/source-pipeline.ts`); `snapshotInput` (`src/cli/state/transform-completion.ts`); `retainedAcquiredInputs`, which checks it; `data reset`, which points it at each acquire in turn to replay it (`src/cli/data/reset.ts`); and `intake workspace migrate-state`, which copies it. None needs anything the list's last entry does not give.
  - `resume` stays, for an unfinished acquire only. The acquire writes it when it starts, pointing at its own output folder, and drops it when it completes; the next acquire of the namespace copies that folder into its own output and passes it in `previousSourceDirs`. In the dev workspace only CourtListener has one, for the acquire of 2026-11-17 that did not complete, and the `cache-call-results-and-files` move deletes it.
  - Whether an acquire is processed is read from the database being targeted (owner's decision, 2026-11-18): an acquire is not considered only when a mutation applied to that database included that exact acquire. Every other listed acquire is considered, oldest first.
  - What exists today. A chain entry is a `DatabaseMutations` envelope (canonical IO `src/cli/import/artifacts/io/DatabaseMutations.ts`, chain code `src/cli/data/chain.ts`). Its metadata records `data-mutation/version`, `data-mutation/previous` (the chain head when the generate started; the chain is a linked list, so that head names every mutation already applied, ADR 0033 §2), `sourceArtifactsName`, `sourceArtifactsPath` (an absolute path to the transform's `Artifacts` file) and `sourceArtifactsDigest`, and `databaseSchema.appliedMigrations`. The database's ledger `data_mutation_applied(version, previous_version, checksum, applied_at)` (`supabase/migrations/20260905000000_data_mutation_ledger.sql`, `src/cli/database/data-mutation-ledger.ts`) records which entries are applied, with each file's checksum. Nothing records which acquires an entry included.
  - What is new. Each generated `DatabaseMutations` envelope also records the acquires it included, each named exactly as an acquire output is named today: its namespace, its command ID (the name of the command folder's `Command` envelope), its output path relative to the intake workspace (`command/<folder>/<namespace>/output`, the form `retainedAcquiredInputs` returns) and the digest of that folder (`directoryDigest` in `src/cli/state/transform-completion.ts`). The mutations already applied when the generate started stay recorded by `data-mutation/previous`. An acquire is processed for a database when an entry in its ledger, whose file matches the ledger's checksum, names that acquire.
  - This is a change to the data shape of the `DatabaseMutations` envelope's metadata, a workspace file `data up` reads; it needs no Supabase migration and touches no generated envelope type or downstream app contract.
  - After the one-time move nothing in the dev database records included acquires, because no existing entry names one. So the first run considers every completed acquire of each namespace, as `data reset` does; no acquire, `latest` included, is marked as processed.
- `gov/irvingtx/arrests` does not follow that model: its acquire reads one fixed folder at the top of the workspace, `gov/irvingtx/arrests/source/`, so it can hold one set of files. Its acquire changes to read the files from its own command folder, where `intake data acquire gov/irvingtx/arrests --from-local <folder>` copies them, so each set of hand-placed files is one acquire command, and every completed acquire is processed in order.
- **Breaking:** all state is under `$INTAKE_WORKSPACE/state/`. Nothing is read from or written to `$INTAKE_WORKSPACE/intake/state/`.
- `state/<namespace>/` holds the state that namespace owns. A namespace is a source ID (the reversed domain of the source's data, `/`-delimited) or `intake`.
- `state/intake/namespaces/<namespace>/<Kind>/` holds what the root intake module keeps about another namespace across commands: the source-name mapping, `PropertyCorrection`, `CallResult` and `BinaryFile` (`src/cli/state/call-cache/index.ts`) and, moved here, `RecordsRequest`.
- `ResolvedProperty` is intake's own state, not state about another namespace, so it moves from `state/intake/namespaces/intake/ResolvedProperty/` to `state/intake/ResolvedProperty/` (owner's decision, 2026-11-18). Intake's own state is never under `namespaces/`.
- Files that come into the workspace by hand or by download follow the folder structure of an automated acquire: what is acquired is saved in a command folder, and the source's `acquire` pointer names that folder. Reply messages and attachments to a records request do not do this today: they are saved under `intake/state/records-request-inbox/`. They change to the command folder of the sync that downloaded them. Files placed by hand enter through an acquire command, never through a folder at the top of the workspace.
- A downloaded file is cached, so it is not downloaded again. The cache is the one `cache-call-results-and-files` defines; this change does not add another.
- `InitialAgencyRoots` moves from `intake/state/namespaces/<namespace>/InitialAgencyRoots/` to `state/<namespace>/InitialAgencyRoots/`: it is the source's own starting set, so it lives in the source's state.
- No folder named `namespaces` sits directly under `state/`, and none sits below another `namespaces` folder.
- A workspace that still has `intake/state/` fails every command that reads state, naming the folder.
- The workspace is moved by a one-time script run against a clone of the workspace, kept outside the repository beside `~/dev/PoliceConductUS/intake-workspace/migration-2026-11-17/` and run as that one was. No migration code or command is added to intake: there is no `intake workspace migrate`, and `intake workspace migrate-state` is not used, because it copies state into a separate workspace, writes a top-level `backups/` folder and throws on a `CallResult` or `BinaryFile` file. The move: each file under `intake/state/` to its new place; `gov/` to `state/gov/`; each file in `state/intake/namespaces/intake/ResolvedProperty/` to `state/intake/ResolvedProperty/`; each file in `media/` into the cache; the `captions` key removed from each video in `state/com/youtube/policeactivity/video-cache.json` (all 65 hold `"captions": null`, so no caption text is lost; captions are no longer fetched); the empty `assets/` and `media/` folders removed. It leaves in place anything it has no rule for. It fails before moving anything when a destination exists with different content, and a second run on the same clone changes nothing.
- AGENTS.md, ADR 0010 and the `artifacts-database-import` spec are corrected to the layout the code has.
