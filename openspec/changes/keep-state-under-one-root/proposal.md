## Why

State is kept in three places: `state/<source id>/`, `state/intake/namespaces/<namespace>/` and `intake/state/`, while AGENTS.md, ADR 0010 and the `artifacts-database-import` spec name a fourth layout. The owner ruled (2026-11-17) that the workspace has one state root, `state/`. A namespace's acquire state is also one pointer, `latest`, so a phase reads only the last acquire, and an earlier acquire not yet processed waits for the next `data reset`. The owner ruled (2026-11-18) that this change fixes both.

## What Changes

How each item is built, and the code it changes, is in [design.md](design.md); its Context describes the code today.

- The workspace top level is `command/`, `state/` and `data/`. `data/mutations/` stays where it is. No command checks the top of the workspace (owner's ruling, 2026-11-18); a test keeps code from writing `intake/state/` again.
- **Breaking:** all state is under `$INTAKE_WORKSPACE/state/`. Nothing is read from or written to `$INTAKE_WORKSPACE/intake/state/`.
  - `state/<namespace>/` is the cross-command state folder a command passed to a source gets. A namespace is a source ID (the reversed domain of the source's data, `/`-delimited) or `intake`.
  - A `namespaces/` folder under a state folder holds that parent namespace's state separated by another namespace (owner's ruling, 2026-11-18). So `state/intake/namespaces/<namespace>/<Kind>/` holds what the root intake module keeps per namespace, for every namespace, `intake` included: the source-name mapping, `PropertyCorrection`, the bytes of its files (`BinaryFile/`) and, moved here from `intake/state/namespaces/<namespace>/`, `RecordsRequest` and `InitialAgencyRoots` (owner's ruling, 2026-11-18; a CLI command writes `InitialAgencyRoots` when one is first needed).
  - `state/intake/<Kind>/` holds intake's state that is not separated by namespace. `ResolvedProperty` moves here from `state/intake/namespaces/intake/ResolvedProperty/` (owner's ruling, 2026-11-18), and a command that finds the old folder fails, naming it.
  - No folder named `namespaces` sits directly under `state/` or below another one: a source ID with a segment named `namespaces`, or of more than one segment whose first segment is `intake`, is rejected; the namespace `intake` itself stays valid.
- `assets/` and `media/` are no longer used. A file's bytes are at `state/intake/namespaces/<namespace>/BinaryFile/<sha256>.<extension>`, and a `BinaryFile` record points at them, as `cache-call-results-and-files` defines.
  - `assets/PersonnelPhoto/` belongs to `cache-call-results-and-files`, which alone moves the photo's bytes into a `BinaryFile` folder and sets the person's `photo_id`. This change removes `assets/` once the photo's bytes are there with the same SHA-256.
  - `media/` holds five files in the dev workspace, in `media/farmakes-voicemail/` (`original.mp3`, `farmakes-voicemail.mp4`, `title-card.png`, `provenance.json`, `youtube-metadata.json`), which no record names. Each file's bytes are copied to `state/intake/namespaces/org/policeconduct/manual/BinaryFile/<sha256>.<extension>` (owner's rulings, 2026-11-18 and 2026-11-19). A `BinaryFile` record is written only for a file a manual record points at, so none is written for these five; the move's README lists them. `provenance.json` keeps the source URL.
- `gov/` goes under `state/` (owner's ruling, 2026-11-17). In the dev workspace its only files are `gov/irvingtx/arrests/source/`, byte-identical (but for an `arrests-normalized.jsonl` no code reads) to the evidence of the Irving acquire in `command/2026-10-26T04-25-42-484Z-icypgxzfk0lnu02mla8qul7t/`. After this change no code reads `state/gov/irvingtx/arrests/source/`.
- The move removes the `captions` key, `null` in all 65 videos, from `state/com/youtube/policeactivity/video-cache.json`. Captions are never fetched (owner's ruling) and no code reads the key.
- Every source supports any number of acquires. Each acquire is a command whose output is in its command folder, and every phase processes a namespace's acquires in the order they ran, which the command folder's name gives (owner's ruling, 2026-11-17).
- **Breaking:** `state/<namespace>/acquire.yaml` holds `acquires`, the ordered list of every complete acquire, and no longer `latest` (owner's ruling, 2026-11-18). An acquire is complete only when it is listed; the separate completion marker goes. The last successful acquire is the list's last entry. An `acquire.yaml` that holds `latest` fails, naming the file. `data reset` no longer rewrites `acquire.yaml`; it gives each command the acquires to take as input.
- `resume` stays as it is, beside the list, and is not part of the list. The owner ruled (2026-11-18) that `resume` and `previousSourceDirs` are removed once every call result and downloaded file an acquire makes goes through the cache, because an interrupted acquire is then run again and gets its earlier answers from the cache. Today only CourtListener's acquire goes through the cache. So `cache-call-results-and-files` and this change keep `resume` and `previousSourceDirs`, and the follow-up change `cache-every-acquire` moves the other four acquires onto the cache and then removes both, after this change's code (design, Migration Plan). The acquire passes the list's last entry where it passed `latest` in `previousSourceDirs`. In the dev workspace only CourtListener has a `resume`, and the `cache-call-results-and-files` move deletes it.
- **Breaking:** run without being given acquires, `data transform` takes every pending acquire of the namespace as input, oldest first, instead of `latest`, and `data generate` generates from that transform; pending means the listed acquires after the newest one the targeted database (the one `DATABASE_URL` names) holds. A listed acquire missing from the database while a later one is in it fails the command, naming both. `data transform` and `data generate` never write to the database; `data update` is the only one that does, and `data reset` writes only through the `data update` it runs (owner's ruling, 2026-11-18). So `data transform` of a source that is not standalone needs `DATABASE_URL`, to read which acquires are applied.
- Whether an acquire is in a database is read from that database (owner's ruling, 2026-11-18). Each generated `DatabaseMutations` envelope records, in `acquires`, every acquire its transform read, identified by the command ID of the command that produced it, with its namespace, output path relative to the workspace and folder digest as evidence. An acquire is in a database when an applied mutation lists its command ID; an applied mutation whose file is missing or differs from the ledger's checksum fails the phase. The list is required on every chain entry, with no compatibility path, so `data reset --no-acquire` runs right after this change's code.
- A source whose files are placed by hand declares `manual: true` (owner's ruling, 2026-11-18). `data acquire` of such a source keeps one active acquire folder, named in `acquire.yaml`, prints its path and tells the person to put the files there; a later `data acquire` completes it once it holds files and makes a new one, and transform and reset skip an empty one as waiting for files. `--from-local` stays, as the one-step form for any source. `gov/irvingtx/arrests` is manual-only and reads its files from its own acquire folder, not from the fixed folder `gov/irvingtx/arrests/source/`. Each set of hand-placed files is one acquire.
- Files that come into the workspace by hand or by download follow the folder structure of an automated acquire. A records request whose answer is files has an acquire folder of its source; the sync, when built to that contract, saves an answer's attachments there (owner's ruling, 2026-11-18). Building it is outside this change; today's reply inbox only moves from `intake/state/records-request-inbox/` to `state/intake/records-request-inbox/`.
- `intake workspace migrate-state` is removed: nothing uses it, and it reads `intake/state/` and `latest`.
- `npm run publish:import-schemas` and its `intake/schemas/` output are removed as dead code; the database is the single source of intake's models (owner's ruling, 2026-11-18).
- The workspace is moved by a one-time script run against a clone, kept outside the repository beside `~/dev/PoliceConductUS/intake-workspace/migration-2026-11-17/` (owner's ruling, 2026-11-17: no migration code in intake). The move is listed in design, decision 12.
- AGENTS.md, ADR 0010, ADR 0033 and the accepted specs below are corrected to this layout and this acquire model.

## Capabilities

### New Capabilities

- `workspace-state-layout`: where each sort of state lives in the workspace; how a namespace's acquires are listed and chosen as input; and how a mutation records the acquires it came from, so a database says which acquires it holds.

### Modified Capabilities

- `agency-record-selection`: `InitialAgencyRoots` is in `state/intake/namespaces/<namespace>/InitialAgencyRoots/`.
- `artifacts-database-import`: the requirements that name `$INTAKE_WORKSPACE/intake/state/...` now name `$INTAKE_WORKSPACE/state/intake/...` "Shared Update State" and "Shared Update State Shape" are rewritten as `ResolvedProperty`, which is what the code does, and "Import Type Registry" loses its schema-publishing scenario, because `publish:import-schemas` is removed (design, decision 10a).
- `current-summary-prompts`: the reset preparation requirement speaks of the acquire list instead of acquisition pointers.
- `data-reset`: reset rebuilds through `data update` from the acquires `acquire.yaml` lists, and no longer rewrites a pointer.
- `intake-stage-completion`: generation requires a transform of exactly the acquires it takes as input, not of `latest`.
- `workspace-source-inputs`: Irving is manual-only and reads its files from its own acquire folder.

## Impact

- Code: the files design.md names, listed with their tasks in tasks.md; `src/cli/workspace/` is deleted.
- Documents: AGENTS.md, ADR 0010, ADR 0033, `docs/records-requests.md`, `sources/gov/irvingtx/arrests/README.md`, and the README files of the folders whose code changes.
- Supabase: no migration and no generated type refresh. The metadata of the `DatabaseMutations` chain files in `data/mutations/` gains `acquires`, which a command run alone reads to find the pending acquires. Each database needs `data reset --no-acquire` right after this change's code (design, Migration Plan, step 3a).
- Workspaces: the dev workspace has nothing under `intake/state/`; its `gov/` goes to `state/gov/`, its `media/` files' bytes into `state/intake/namespaces/org/policeconduct/manual/BinaryFile/`. Every other workspace is moved the same way before this change's code runs on it (design, Migration Plan).
- Downstream: checked 2026-11-18, policeconduct.org's `main` names no `assets/` or `media/` of the intake workspace, and parses no chain file: it names `INTAKE_WORKSPACE` only in documents that tell an operator to run intake's `data` commands, and where a reset keeps `command/.../previous-mutations/`. So it needs no change.
