# Design: work out CourtListener complaint summaries in generate, and never drop a case over its complaint

Related documents: [proposal](proposal.md), [complaint summaries spec](specs/courtlistener-complaint-summaries/spec.md), [record findings spec](specs/record-findings/spec.md), [tasks](tasks.md), [cache design](../cache-call-results-and-files/design.md), [ADR 0040](../../../docs/adr/0040-sources-and-resolvers-report-findings-that-become-annotations.md), [ADR 0039](../../../docs/adr/0039-the-cache-holds-call-results-and-files.md), [existing summary spec](../add-ai-complaint-summary/specs/ai-complaint-summary/spec.md).

This design replaces an earlier one, reviewed on 2026-11-16, that kept the summary in acquire. It is described under "Alternatives considered".

## Problem statement

Intake runs in phases, each a command:

1. **`data acquire <source>`** fetches a source's raw records into a command folder.
2. **`data transform <source>`** turns them into artifacts: lists of records of a kind, such as civil cases.
3. **`data generate <source>`** compares the artifacts with the database and writes the changes needed, as mutations. Fields that a source does not supply are worked out here by resolvers. Annotations are written here.
4. **`data up`** applies the mutations.

`data reset` rebuilds the database by running these for every source in order, including acquire.

The CourtListener source finds federal civil dockets that name a police agency. A docket is one court case on CourtListener. Today its acquire does three things for every docket it finds, about 8,300 of them:

- fetches the docket's entries (the list of documents filed);
- downloads the complaint, the document that starts the lawsuit, as a PDF;
- asks Claude for a summary of it.

Two things are wrong.

1. **One complaint with a problem stops everything.** The acquire throws on a problem with one docket's complaint. On 2026-11-16 it stopped at its 85th docket because the SHA-1 CourtListener records for a PDF differs from the file it serves. A failed acquire also stops `data reset` at that source, so no later source is rebuilt.
2. **Most of the work is discarded.** The transform keeps a docket only when one of its parties matches an officer of the agency. The database holds 551 civil cases. The acquire fetches, downloads and summarizes for all 8,300.

## Goals

- A CourtListener acquire finishes, and so does a `data reset`, once the manual source holds a licensing authority for every state an agency is in (section 6).
- A case is imported whether or not its complaint can be summarized. A problem is stated on the case as an annotation, in plain English, with the address where the complaint can be read or bought.
- Entries, PDFs and summaries are fetched only for dockets that become cases, and only once while nothing has changed.
- A docket that is left out is logged with the reason.

## Non-goals

- The cache and the shared clients. They are designed in `cache-call-results-and-files`; this design uses them.
- The typed annotation envelopes of `type-annotation-envelopes` and ADR 0038. This change uses today's annotation shape.
- Any change to policeconduct.org. It shows an annotation's message as intake writes it.
- Summaries for civil cases from other sources. The resolver acts on any case that names a CourtListener docket, but only the CourtListener source supplies one today. The resolver chooses a case by the host of its primary source URL, which is data, not by the source's namespace, so it is not a special case by namespace (AGENTS.md).

## Terms

- **Entries**: the list of filings on a docket. Each entry can have documents.
- **Complaint**: the document that starts a lawsuit. The resolver selects the latest one identified in the entries (`selectComplaint` in `src/cli/import/artifacts/facades/complaint-summary-resolvers.ts`): the candidate with the highest entry number; within one entry, an explicitly labelled complaint attachment wins. The rules for a labelled attachment and for a duplicate entry with no number are the scenarios of "Available complaint without a reliable summary" in the [existing summary spec](../add-ai-complaint-summary/specs/ai-complaint-summary/spec.md).
- **Resolver**: code in the shared import that works out one field of a record during `data generate`. Geocoding an agency's address is an existing one.
- **Cache**: the `ResolvedProperty` envelopes, intake's one cache. A call result is a call entry in it, filed under the record the call is made for (here the `CivilCase`) and the client operation (`cache-call-results-and-files`, section 1).
- **Client**: shared code that calls one outside service through the cache, from `cache-call-results-and-files`. It returns a result, an item failure the caller can act on, or "skipped" when its service is down. Which answers are item failures and which are outages is section 4 of that design: a 429, a 5xx, no answer, or a 401, 403, account or credit error that outlasts the retries is an outage only when the service check, run again, also fails; otherwise it is an item failure. A service is down when it went down during the run or an outage recorded on an earlier run is still inside its wait (an hour, unless the service gave a time). Before its first call that the cache cannot answer, a client checks its service (the inference check also confirms that the model asked for exists); if the check fails, the command exits non-zero there, naming the service. A run that the cache answers wholly checks nothing.
- **Annotation**: a database record attached to another record that reports a problem with a source's data. It has a type (warning, error or correction), a field, a value, a message and evidence.
- **Finding**: a problem reported about one record, before `data generate` turns it into an annotation.
- **Unavailability state**: the existing `complaint_summary_unavailability` field on a civil case. It holds a reason, a detail, a source URL and a time. Its reasons are an existing fixed list.
- **Licensing authority**: the record for a US state's officer licensing body, for example TCOLE (the Texas Commission on Law Enforcement). It is the record intake uses to stand for a source of officers.
- **Partial update**: a record with `metadata.action: PATCH` that changes only the fields it carries on the one existing record its `metadata.selector` matches ([ADR 0034](../../../docs/adr/0034-manual-updates-by-selector-and-workspace-coupled-chain.md)). The import fails when the selector matches no record or more than one.
- **The owner**: Dale Lotts, who decides this project's open points. A decision is dated where it is cited.

## Proposed architecture

### Overview

```text
acquire      CourtListener client: search per agency ──> <agency>.dockets.json
transform    match parties to officers ──> CivilCase records, each with its docket's address
                                       ──> one LicensingAuthorities partial update per state,
                                           with docket-not-buildable findings
generate     civil case resolver, per case:
               CourtListener client: entries ──> select complaint
               download client: PDF ──> check it
               PDF text client: text
               inference client: summary
             success ──> summary on the case
             problem ──> unavailability state on the case + finding ──> annotation
up           applies the mutations
```

Every arrow to a client goes through the cache. A second `data generate` with nothing changed makes no request.

### 1. Acquire lists dockets and nothing else

`acquire.ts` keeps its loop over agencies and its search, now made through `CourtListenerClient`. A successful search result carries a `retryAfter` 120 days ahead, the refresh interval the source's own docket cache used before this change. The acquire writes `<agency source ID>.dockets.json`, the ID encoded with `encodeURIComponent`, as soon as that agency's searches are done, and nothing else. A search that finds nothing is a success. When a search fails for one agency (an item failure), or is skipped because CourtListener is down, the acquire writes no file for that agency, makes every other search and writes the other agencies' files, then exits non-zero naming each failed or skipped search, and is not recorded as completed (owner's ruling, 2026-11-19; `cache-call-results-and-files`, section 4). A later transform therefore never reads a run that left an agency out. Running the acquire again calls only what the cache does not answer.

The acquire still stops, naming the agency, for an agency with no name, for an agency in a state with no list of federal courts (which cannot happen today, because the acquire asks only for agencies in those states), and for a search result with no docket ID or no list of parties. The search that returned such a result is already a successful call entry that stands for 120 days, so every acquire in that time stops at the same place until the entry is retired with the `intake cache` operation that retires a bad stored result, with its required `--message` (`cache-call-results-and-files`, section 3). `COURTLISTENER_MIN_YEAR` (default 2022) sets the earliest filing year searched; a value that is not a whole year stops the acquire.

A `dockets.json` holds `agency` (`id`, `name`, `state`, `county`, `place`) and `dockets`, each with `id`, `case_name`, `docket_number`, `court`, `date_filed`, `date_terminated`, `cause`, `absolute_url` and `parties`.

Removed from the acquire: the entries requests, the PDF downloads, the model calls, `docket-cache.json`, `.api-calls.jsonl`, the `complaints/` folder, and the catch that skipped an agency on any error.

### 2. The transform stops supplying the summary and logs what it leaves out

Each `CivilCase` record already carries its docket's address on CourtListener as `primary_source_url`. The resolver finds the docket from that address, so no field is added to the case and the database does not change. The Clearinghouse source emits some of the same cases, by the same natural ID, with its own address as `primary_source_url`; in a Clearinghouse run the resolver finds no docket and leaves the fields as that source supplied them (section 3).

The transform no longer supplies `ai_complaint_summary` or `complaint_summary_unavailability`.

It checks each docket in this order and counts each outcome for its last log line:

1. **The agency record in the file lacks an ID, a name or a state:** the transform fails, naming the file (section 7 of the `report-every-left-out-source-record` design). So does a file that cannot be read, a file with no list of dockets, and a docket with no ID or no address.
2. **No party matches an officer of the agency:** leave the docket out; log the docket ID, its URL and "no matching officer".
3. **A party matches but the docket has no title, or no filing date that starts with `YYYY-MM-DD`:** write no case; report a finding on the licensing authority (section 6).
4. **Otherwise:** write the case. A docket that reaches this step with no court, no docket number, or a termination date that is not a date fails the transform, naming the file and the docket; none of the 48,316 docket rows in the dev workspace is like that. When a later docket gives a case that is already written different content, the later one replaces it and the transform logs both dockets; whether that is right is an open question of `report-every-left-out-source-record`.

Officer matching runs before the title and date check, so that only a docket that would have become a case can produce the finding in step 3.

### 3. The civil case resolver

One resolution per case fills both `ai_complaint_summary` and `complaint_summary_unavailability`, the way one geocode fills both latitude and longitude today. It runs only when the case's `primary_source_url` is a docket address on `www.courtlistener.com` (`https://www.courtlistener.com/docket/<digits>/…`); `docketIdFromUrl` in `src/shared/services/courtlistener-client.ts` reads the docket ID from it. For any other address the resolver returns the values the case's source supplied and reports nothing. Resolver findings are grouped by the source namespace of the artifact that carried the record (section 5), so a Clearinghouse run neither changes the summary fields nor resolves CourtListener's annotations. The steps:

| Step                                                           | Client        | Item failure or bad result   |
| -------------------------------------------------------------- | ------------- | ---------------------------- |
| Fetch the docket's entries                                     | CourtListener | `complaint-entries`          |
| Read the entries' complaint candidates                         | none          | `complaint-entries-unusable` |
| Select the latest identified complaint                         | none          | `complaint-not-found`        |
| Is a copy available, with a download address?                  | none          | `complaint-no-copy`          |
| Download the PDF from `storage.courtlistener.com`              | Download      | `complaint-download`         |
| Does the file start with `%PDF-`?                              | none          | `complaint-not-pdf`          |
| Does CourtListener record a SHA-1 of 40 lower-case hex digits? | none          | `complaint-no-check`         |
| Does the file's SHA-1 equal the recorded one?                  | none          | `complaint-mismatch`         |
| Extract its text                                               | PDF text      | `complaint-no-text`          |
| Ask for a summary; check the pages it cites exist              | Inference     | `complaint-no-summary`       |

A download address that is not on `storage.courtlistener.com` counts as no download address (`complaint-no-copy`). A text extraction that fails, or that finds no text on any page, is `complaint-no-text`; this includes a file that starts with `%PDF-` but that the PDF tools cannot open, and a PDF program that runs past its time limit, is killed or overflows its output for that file (owner's ruling, 2026-11-19). The time limit per program run is set by the PDF text client (`cache-call-results-and-files`, section 4). A summary that cites a page number above the file's page count is `complaint-no-summary`, and so is any other item failure of the model call: a stop for any reason but the end of the answer, an answer that is not JSON or does not fit the output schema, a response that names no model, and an API error the client counts as an item failure (for example a complaint too long for the model). Entries that do not have the expected shape, or a complaint candidate with no entry number or with a filing date that is not a date, are `complaint-entries-unusable`: the list was fetched, but no filing in it is a usable complaint. `complaint-entries` is only for a list that could not be fetched (owner's ruling, 2026-11-19).

Every row but two ends the work on that case. `complaint-no-check` and `complaint-mismatch` do not: the resolver reports the finding and goes on to extract the served file's text and ask for a summary, and the summary's source records `sha1Verified: false` (owner's decisions: a mismatch, 2026-11-17; no recorded SHA-1, 2026-11-19). A file with no recorded SHA-1 is not compared, so it gets `complaint-no-check` and never `complaint-mismatch`.

The rule for outages is the clients', not this resolver's. A failure of one item comes back as a value and becomes a row in this table. When a client answers "skipped", the resolver stops work on that case, leaves both fields as they are and calls `keepFindings()`: the case keeps any summary and state it had, gets no new annotation, and is tried again on the next run. `data generate` prints the skip lines and exits zero; only `data acquire` fails at its end on skipped or failed calls (owner's ruling, 2026-11-19). A problem with the case's own data is one of these ten codes; an entries response that does not have the expected shape is `complaint-entries-unusable`, not a thrown error. A fault in intake or its tools still stops the command, as AGENTS.md requires: a PDF program that cannot be run at all (its check fails), a file a download entry names whose bytes are missing from the workspace or do not match its SHA-256, or a stored summary that does not fit the `ai_complaint_summary` schema.

**When a problem is tried again.** A call entry's current outcome stands until its `retryAfter` passes or its request changes (`cache-call-results-and-files`, section 3). A successful entries result carries a `retryAfter` 120 days ahead, so new filings on a docket are seen at that interval. Every item failure carries one 24 hours ahead, so a failed entries call, download, text extraction or model call is tried again the next day (owner's ruling, 2026-11-19). An outage carries one too (see **Client** under Terms). A successful download, text extraction or model answer carries none, so it stands until its request changes. The download request is the file's address alone: a successful download is asked again only when a refreshed entries result gives a different file address. A refreshed entries result that records a different SHA-1 for the same address is compared with the file already kept, so a mismatch clears when CourtListener corrects its record, but not when it replaces the file behind the same address; such a stored result is retired with the `intake cache` operation that retires a bad stored result, with its required `--message`, and the next run downloads again. A successful model answer is asked again only when the prompt, the parameters or the text change. During `data reset --no-acquire`, the latest succeeded outcome is used even after its `retryAfter` and even when a later attempt failed (`keepSucceeded`, owner's ruling, 2026-11-19), so a reset and a `data generate` can give one case different states.

**The request to the model** holds its parameters (`maxTokens` 4096 and the output schema: paragraphs, each with its text and the pages it cites), the full prompt text, and the SHA-256 of the complaint's text. It sets no reasoning level. The model and the prompt are the constants `COMPLAINT_SUMMARY_MODEL` and `COMPLAINT_SUMMARY_PROMPT` in `complaint-summary-resolvers.ts`. Changing the prompt or the parameters therefore asks again for every case, and reuses the cached entries, PDF and text. The model is not in the request (`cache-call-results-and-files`), so changing `COMPLAINT_SUMMARY_MODEL` asks nothing again. The summary's `model` is the model the response named, read from the call's outcome, not the model asked for.

**The text** comes from the PDF text client, not from CourtListener's own extracted text. The pages are sent to the model joined by a form feed. That gives CourtListener and Minnesota POST one way of reading a PDF, including OCR for a scanned page.

**The stored summary** holds the summary text (the answer's paragraphs joined by a blank line), `model`, `generatedAt` (the date of the model call), `support` (the pages each paragraph cites) and `source`: the complaint's page on CourtListener (`sourcePage`), CourtListener's document ID and number, the filing date, `retrievedAt` (the time of the download) and `sha1Verified`. The file itself is not described in the summary: it is a `BinaryFile` record, and the case points at it (below). The summary's `url`, `sha1` and `sha256` are no longer written and are removed from the `aiComplaintSummary` schema; CourtListener's recorded SHA-1 is in the entries call entry and in the finding's value. The fixed texts `confidence`, `limitations` and one `proceduralContext` line that names the complaint and its filing date are carried over from the acquire's earlier summary. There is no publication status and no review step for publication (owner's ruling, 2026-11-19): `publicationStatus` is removed from the resolver's output and from the `aiComplaintSummary` schema in `src/shared/ai-complaint-summary.ts`. The `civil_cases` check does not list allowed keys since `20261111230000_relax_complaint_summary_requirements.sql`, so removing summary keys needs no change to it, and no stored summary holds them today.

**The complaint's file is a `BinaryFile` record.** A record that has a file points at the file's record with a foreign key and copies nothing else about it (`cache-call-results-and-files`, section 2). `civil_cases` gains `complaint_file_id`, a foreign key to `binary_file`, set whenever the resolver downloaded the complaint's file, whether or not a summary was made, and null otherwise. The resolver backend stores the downloaded bytes under the case's source namespace, and a `BinaryFile` record for them, with the file's SHA-256 as its source name, is written by the same `data generate` as the case; `complaint_file_id` is filled by the standard foreign-key resolver. This needs one Supabase migration (the column and its foreign key), after the migration of `cache-call-results-and-files` that creates `binary_file`.

**Nothing derived here is cached a second time.** There is one cache (owner's ruling, 2026-11-19). The summary and the state come only from call entries of that cache, so they are worked out on every run from those entries and are not cached again under their own property; the generated `RESOLVED_PROPERTIES` leaves them out. The run makes no request when nothing has changed, and a failure is not frozen in place. AGENTS.md's rule that a resolved value goes through `ResolvedProperty` holds, because the calls it comes from are there (`cache-call-results-and-files`, section 1).

### 4. A problem becomes a state and a finding

For each code the resolver sets the unavailability state and reports one finding. No new reason is added to the existing list.

| Code                         | Unavailability reason  | Finding type |
| ---------------------------- | ---------------------- | ------------ |
| `complaint-entries`          | retrieval_failed       | warning      |
| `complaint-entries-unusable` | pending                | warning      |
| `complaint-not-found`        | pending                | warning      |
| `complaint-no-copy`          | missing_copy           | warning      |
| `complaint-download`         | retrieval_failed       | warning      |
| `complaint-no-check`         | none: summary written  | warning      |
| `complaint-mismatch`         | none: summary written  | error        |
| `complaint-not-pdf`          | retrieval_failed       | error        |
| `complaint-no-text`          | available_unsummarized | warning      |
| `complaint-no-summary`       | available_unsummarized | warning      |

An error is a case where CourtListener's own data is wrong or contradicts itself. A warning is a case where something is absent or could not be used; a missing or malformed recorded SHA-1 is absent, so `complaint-no-check` is a warning, and both entries codes are warnings (owner's ruling, 2026-11-19). `available_unsummarized` is the reason the existing summary spec defines for a complaint that exists but has no reliable summary.

The finding holds:

- `code` and `type` from the table;
- `field`: `ai_complaint_summary`;
- `value`: what was found. For a mismatch: `recordedSha1`, `servedSha1`, `servedSha256` and `bytes`. For `complaint-no-check`: `recordedSha1` as CourtListener gives it (null when it gives none) and `servedSha256`. For a download failure: the HTTP status, or null when the failure had none. For the others: the document number as CourtListener gives it (it may be blank) when a complaint was identified, otherwise null;
- `message`: the text in the spec for that code, with the address filled in;
- `evidence`: one source record each for the docket, the complaint document when identified, and the downloaded file when there is one. Each has `what` (`docket`, `complaint document` or `downloaded file`), `source_namespace` and `url`; the downloaded file also has `retrieved_at` and `sha256`. The docket and the complaint document are pages, not files, so they carry no retrieval time. When the complaint has no page of its own, its record's `url` is the docket's;
- the source namespace and the docket ID as its source record ID.

The state's `detail` is the same message. Its `checkedAt` is the time of the call result that decided the outcome, so it does not change from run to run while that result stands.

**The message says three things and no more:** that we tried to summarize the complaint, why we could not, and where to look. The `complaint-mismatch` and `complaint-no-check` messages differ: a summary was made, why it should not be trusted or could not be checked, and where to look. It gives the docket's address, or the complaint document's page when there is a file to point at. When there is no free copy it also says how a reader can help: buying the complaint from PACER, the federal courts' document system, with the free RECAP browser extension installed makes it free for everyone on CourtListener, with a link to the setup page (`https://free.law/recap/`). Apart from that setup page, a message gives no address on any host other than `www.courtlistener.com`; the download address on `storage.courtlistener.com` appears only in the evidence and the summary's source.

The message wording is in the spec, because it is public text.

### 5. Findings in the shared import

Today `data generate` builds two groups of findings per record (corrections applied, and validation of the final values) and turns each finding into a `DataAnnotation` record. The record's name is a hash of the subject, the group, the finding's key, the source namespace and the source record ID, and its ID comes from that name, so it is the same on every run. An active annotation in a group that the record no longer produces is written as resolved.

This change adds two groups:

- **Source findings:** the list in a record's `metadata.defects`.
- **Resolver findings:** what a record's resolvers reported through their context.

A finding's key is its code and field. Because the name already includes the source record ID, two findings with one code about two dockets are two annotations.

The source-findings group of a record is also separate for each source namespace whose artifact carried the record, in the same way the corrections group is separate for each contributing source. Several sources report on one state's licensing authority, so a run of one source resolves only the annotations that source reported.

The source-findings group exists only for a record whose metadata holds `defects`. An empty list resolves that source's earlier findings on the record. A record with no `defects` in its metadata leaves earlier source findings as they are.

A finding has no `code` column to land in; the code is used for the name and is not stored on the annotation. ADR 0038 gives it a home later.

`metadata.defects` cannot reach the import today, because record metadata is rebuilt from `name`, `action` and `selector` at each of these places: `toRecordMetadata`, the singular record envelope and the artifact write path in `scripts/generate-envelope-types.ts`; `src/shared/io/Artifacts.ts`; `src/cli/import/artifacts/config.ts`; and the `EmittedRecords` type in `src/cli/transform/source-transform.ts`. Each is changed to validate the metadata once against its strict schema and pass the object on whole.

The resolver-findings group of a record is also separate for each source namespace whose artifact carried the record, as the source-findings group is (owner's ruling, 2026-11-19). A run of one source therefore resolves only the resolver annotations made in that source's runs: a Clearinghouse run of a case that CourtListener also emits leaves CourtListener's complaint annotations as they are.

A resolver that could not decide, because a client answered "skipped", calls `keepFindings()` on its context. The resolver-findings group of that record and that source namespace then resolves nothing: the annotations from earlier runs stay as they are. A case of a CourtListener artifact whose primary source URL is not a CourtListener docket gets no complaint finding, so its earlier complaint annotations from that source are resolved.

A finding on a kind that takes no part in annotations (one with no source evidence) fails `data generate`. Today the inspection returns early for such a kind, which would drop the finding silently.

### 6. A docket that cannot build a case

The transform emits one `LicensingAuthorities` record for each US state it processed agencies for, as a partial update that changes no field and carries `metadata.defects`. Its selector is `{ location_path: { path: "/<state in lower case>/" } }`. The shared helper `stateAuthorityRecords` in `sources/lib/state-authority-findings.ts` builds these records; the Clearinghouse and PSV arrest-tracker transforms use it too (`report-every-left-out-source-record`). The list holds one `docket-not-buildable` warning per such docket, with the docket as the finding's source record ID, and is empty when there are none. Emitting the record every time is what lets `data generate` resolve an annotation once its docket is fixed.

The finding's `field` is `civil_cases`, the table the case was not written to; its `value` holds the docket's `case_name` and `date_filed` as CourtListener gave them; its `evidence` is one entry holding the docket's `url`. A docket found for two agencies of one state is reported once, with the first agency's message; the transform's last log line counts every docket row left out this way, so the count can exceed the annotations.

The acquire only lists agencies with at least one officer. Texas, Minnesota and Oregon each have one licensing authority. The last full acquire in the dev workspace (2026-09-28) also has six agencies in DC, one in Virginia and one in Illinois, which have no licensing authority today. Every state an agency is in gets a licensing authority record, created through the manual source (owner's ruling, 2026-11-19); the source does not create one. Because the transform emits the record even when its list is empty, `data generate` for CourtListener fails, naming the selector, for a state whose licensing authority the manual source does not yet hold, and so does `data reset`. Before the next reset, the manual source therefore gets a licensing authority for DC, Virginia, Illinois and every other state the workspace's agencies are in (task).

## Alternatives considered

- **Keep the summary in acquire and record problems there.** This was the design reviewed on 2026-11-16. Rejected: it kept the cost of 8,300 dockets, needed a cache of its own, and the review found its reuse rule skipped a changed prompt.
- **Fetch entries in acquire and only download and summarize in generate.** Rejected: entries for 8,300 dockets would still be fetched to serve 551 cases. With one shared CourtListener client, the resolver can fetch them.
- **Detect a changed docket by CourtListener's index timestamp.** Rejected: nothing in the repository reads it, its meaning is untested, and at 551 cases a refresh every 120 days costs little.
- **Carry the problem only in the unavailability state, with no annotation.** Rejected (owner's decision, 2026-11-17): an annotation is how intake shows a problem with a source's data, it carries evidence and a stable ID that the state does not, and its wording belongs to intake, not to a website component that interprets a reason.
- **Report a docket that cannot build a case through `source_exclusions`.** Rejected: that field records a person's decision to exclude a record, has no place for an address or evidence, and requires one licensing authority mapped to the source's namespace, which a national source does not have.
- **Put that finding on the agency.** Not chosen (owner's decision, 2026-11-17): a record that cannot be built is reported on the record that stands for the source, which is the licensing authority today, so every source reports its left-out records in one place (`report-every-left-out-source-record`). Every state an agency is in gets a licensing authority through the manual source (owner's ruling, 2026-11-19), so the licensing authority always exists.
- **Throw from the resolver and catch per record.** Rejected: the reason would be lost, and an outage would be caught the same way as a problem with one document.
- **Stop the command when a service goes down during the run.** Rejected (owner's decision, 2026-11-17): stopping throws away the rest of the run's work for a problem that clears on its own. Skipping lets the rest finish; the skipped cases keep what they had and are done on the next run.
