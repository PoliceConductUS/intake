## Context

Before this change, annotations reached the database by two routes, both run by intake in `data generate`: a correction applied to a record, and a validation problem in a record's final values. A record excluded by hand with `data exclude` is written into `source_exclusions` on the licensing authority mapped to the source. A source's own code had no way to say that it left a row out. `record-findings` (from `move-complaint-summaries-to-generate`, done first) adds that: a record may carry findings in `metadata.defects`, and `data generate` turns each into an annotation with a stable ID and resolves it when the source no longer reports it.

A licensing authority is the `LicensingAuthorities` record for a state's officer licensing body. The dev database has one for Texas, Minnesota and Oregon. The "drift check" named below is a read of every source's code against its README on 2026-11-17.

## Goals and non-goals

Goals: every row a source reads ends in one of the outcomes of decision 1; a reader of the site can see each row a source could not build or had to change; a row that is not selected is counted and logged, because it is not part of the public record the source covers; and a transform that counts a row as read and gives it no outcome fails.

Non-goals: a call that fails because a service is down (decision 5); an agency that drops out of a source's list (agencies are not removed from the database, so the owner does not consider it yet); the `daily` phase of `com/serpapi/landing-page-search`, which reads no rows into records; annotations for `gov/census/www2/gazetteer`, whose location paths no licensing authority stands for; the CourtListener docket cases, which `move-complaint-summaries-to-generate` specifies. An acquire states no row accounting: the conditions of an acquire are listed in decision 6, and a row an acquire leaves out with no count is found only by a review such as the drift check (a risk below).

## Decisions

### 1. The outcome of each row

A row that builds a valid record with nothing changed is emitted. Every other row has one of these four outcomes, and there is no fifth:

| The row                                                                                                                                                                                                                                                 | What the source does                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Cannot be built into a valid record                                                                                                                                                                                                                     | Emits no record; reports a finding on the licensing authority           |
| Is built, with a value corrected, replaced or left off                                                                                                                                                                                                  | Emits the record with the finding on it                                 |
| Is bad in a way good data cannot be                                                                                                                                                                                                                     | Throws; the command stops and names the source, the row and the problem |
| Is read but not selected: it names no officer or agency the database knows, is outside the source's stated scope, adds no fact an emitted record lacks (for example a second separation), or a person excluded it in `excluded.yaml` before the acquire | Counts it under a named reason and logs the counts                      |

"Cannot happen in good data" is decided per case. The test is whether the source's real data has ever shown the condition; a condition that real data has shown is never a throw. The cases are listed in decision 6 and decision 7; each source's list of the conditions that make it throw lives in its README, ideally generated from the code so it never goes out of date (owner's ruling, 2026-11-19). The TCOLE workbook of 2025-02-10 has no blank ID column in any of its four sheets (`DEPARTMENT_NUMBER`, `PUBLIC_GUID`, `LICENSE`, `LICENSE_ACTION`, where the sheet has the column) and no repeated department number or officer GUID, so a blank ID there throws.

A row that is not a row of data (an empty PSV line) is not read, so it is not counted. A case whose outcome waits for the owner is marked "open question" and is listed under "Open questions"; the code keeps the behavior "Open questions" describes for it until the owner rules.

### 2. Which licensing authority

The finding goes on the licensing authority the row's data belongs to:

- a licensing source (TCOLE, Minnesota POST, Oregon DPSST) reports on its own authority;
- any other source reports on the licensing authority of the state of the agency the row is about, the rule `move-complaint-summaries-to-generate` already uses for a docket.

When a source cannot tell which state a left-out row belongs to, it throws. A finding is never attached to an arbitrary record.

A source that reports on state authorities does not create them. TCOLE, Minnesota POST and Oregon DPSST emit their own authority with its fields; `org/policeconduct/manual` can create one for another state. For each state whose agencies it read in the run (PSV, whose rows name no agency, uses each state its rows name), the source emits a `LicensingAuthorities` record that updates no field: a `PATCH` with the selector `{ location_path: { path: "/<state>/" } }`, the state in lower case, and `metadata.defects`, which is an empty list when it has no findings, so that an earlier annotation is resolved (`sources/lib/state-authority-findings.ts`). A state value that is not a two-letter code throws, and so does a finding for a state the source did not read. A state the source did not read in a run is not emitted, so its earlier annotations stay as they are until a later run reads it. Every state an agency is in gets a licensing authority record, created through `org/policeconduct/manual` (owner's ruling, 2026-11-19, answering `move-complaint-summaries-to-generate` section 6); until it exists, `data generate` fails naming the selector. A run that did not fully cover an authority (an agency whose search failed or was skipped, an Oregon acquire of some name prefixes) emits it with no `defects` key, so its earlier annotations stay (owner's ruling, 2026-11-19). The update needs the authority to be applied first. `src/cli/transform/source-order.ts` orders sources by the foreign keys of the kinds they produce. CourtListener, Clearinghouse and PSV run after the licensing sources through the `AgencyPersonnel` foreign key of the records they emit (`CivilCasePersonnel`, `CoverageLinkAgencyPersonnel`), so the Texas, Minnesota and Oregon authorities exist first. `org/policeconduct/manual` is standalone, and `src/cli/data/source-pipeline.ts` leaves standalone sources out of the run order, so no source is ordered after it: an authority it creates for another state must be applied before those sources run, and nothing declares that. Listing `LicensingAuthorities` in `produces` also makes the planner treat these sources as producers of that kind, and its `location_path_id` foreign key orders them after `gov/census/www2/gazetteer`. The owner ruled on 2026-11-19 that an authority `org/policeconduct/manual` creates is applied first and that a kind a source only updates is not treated as one it produces (task).

### 3. What a finding holds

The fields `record-findings` defines: a code that names the sort of problem, the type, the field, the value found, a plain-English message, the source namespace, the source record ID, and evidence. For a left-out row the source record ID is the row's own ID in the source (a docket ID, a license number, a workbook row), and the evidence is one source record that says where the row can be seen. A row with no ID of its own uses the file name and row number.

The row number need not be perfect; it must be stable and predictable (owner's decision, 2026-11-17). When a table lists the newest row first, its rows are numbered from the oldest: the last row is 1. A row added at the top then changes no earlier row's number. When the table runs over several page files, the count runs through all of them from the last row of the last page, and the name is the officer's file name with the page number left out (`officer-<DPSST number>-employment`), because a new row can move an earlier row to the next page. Oregon DPSST employment findings are named `officer-<DPSST number>-employment#<row>` this way; a finding about a whole employment uses the number of the row that started it. The evidence still gives the page file and the row's place on that page. The Minnesota employment-history workbook and the PSV workbook number their rows from the top (`<file>#<row>`); whether that is stable for them is an open question.

### 4. Row accounting

`SourceManifest` gains `accounting`: for each input the transform reads, the number of rows read, emitted, reported, and not selected by reason. An input is a list of rows the source names: a sheet, a kind of file (all `.dockets.json` files are one input), a series of pages, or a list within one file. A row emitted with a finding on its record counts as emitted; a row any of whose records is left out with a finding counts as reported, even when another record it feeds is emitted (a TCOLE `Services` row with no start date: its license is emitted, its assignment is left out). The shared transform step fails when read does not equal the sum of the others, naming the input and the difference, and logs the totals when the transform ends. `org/policeconduct/manual` has no source rows; it counts each record it reads from its manual output in its state folder as read and emitted, and states zero when there is none. `gov/az/post/roster` reads no input (its transform is turned off and emits nothing), so its accounting is an empty list.

A row that feeds several records (a TCOLE `Services` row feeds a license, an authority license and an assignment) is counted once, at the sheet it was read from. A row left out because the record it depends on was left out is counted as reported under the finding of the record it depends on and gets no annotation of its own.

The counts are kept by the source. The check fails a command when a row is counted as read and given no outcome, so a bare `continue` after the row is counted fails. It does not see a row that is never counted as read, so a source takes `read` from the size of the input where it can (TCOLE uses the number of rows in the sheet). `excluded.yaml` is used at two moments. The Minnesota POST acquire skips an agency it lists, and the transform counts that agency as not selected under `excluded`. The shared step applies it to the records after the transform; the counts the source states are taken before that, so a record excluded there counts as emitted. The shared step also fails on an input with a blank name. The shared step also fails when a source states no accounting or a value that is not a whole number of zero or more. `test/architecture.test.ts` checks only that each source transform's text states `accounting`; the type of `SourceManifest` and the runtime check are what enforce it. A row counted as reported is not checked against a finding; each source's tests give the expected findings and counts.

### 5. Calls that fail are not part of this change

A call the service answered with an error (an item failure) is tried again after 24 hours, and a call skipped because the service was down is tried on the next run; the one cache of call results (`cache-call-results-and-files`) decides that. An empty search result is a success. Only `data acquire` fails for these: it makes every other call and then exits non-zero naming each failed or skipped call; `data generate`, `data update` and `data reset` print the skip lines and exit 0 (owner's rulings, 2026-11-19). This change covers rows and inputs, and the acquire conditions that are data problems, not service problems.

## Alternatives considered

- **Write left-out rows to `source_exclusions`.** Rejected in `move-complaint-summaries-to-generate` for the same reason: that field records a person's decision to exclude a record and has no place for a reason code, an address or evidence.
- **Log every left-out row and write no annotation.** Rejected: a log is not visible to a reader of the site, and a gap in the public record must be.
- **Only fix the known cases, with no accounting.** Rejected: the next source would repeat the fault and nothing would catch it.
- **Count rows in the shared step from the records a source emits.** Rejected: the shared step does not know a source's rows, and one row can feed several records or none.
- **Have the shared step hand out a handle for each row read, and fail on a handle with no outcome.** Not chosen: every transform would be rewritten around the handle, and it still depends on the source asking for a handle for each row it reads, which is the same trust the counts need.
- **Name an Oregon employment row by its content (date, action, agency, rank) instead of its number.** Not chosen: two identical rows can occur, so content alone needs an occurrence count, which moves the same way a row number does when an older row is removed.
- **Report a left-out row on the agency it is about, or the nearest record that exists.** Not chosen: the owner's rule is that a record that cannot be built is reported on the record that stands for the source, the licensing authority (`move-complaint-summaries-to-generate` section 6). The agency can itself be the record that was left out, and one licensing authority per state gives a reader one place to look; the cost is a state with no authority record and the run order of decision 2.
- **Keep one Oregon employment running through a leave and a return, or mark an end date as a leave.** Not chosen: the accepted requirement makes `AgencyPersonnel` service, not uninterrupted employment, so a return starts a new record; no field for the kind of end exists, and adding one is a schema change.
- **End an Oregon employment on the leave date and report the later separation as a finding.** Rejected: the separation is a real event that ends the employment, and the leave date would show the officer leaving months before the separation the department recorded.
