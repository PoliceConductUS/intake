## Context

Annotations reach the database today by two routes, both run by intake in `data generate`: a correction applied to a record, and a validation problem in a record's final values. A record excluded by hand with `data exclude` is written into `source_exclusions` on the licensing authority mapped to the source. A source's own code has no way to say that it left a row out. `record-findings` (proposed in `move-complaint-summaries-to-generate`) adds that: a record may carry findings in `metadata.defects`, and `data generate` turns each into an annotation with a stable ID and resolves it when it is no longer reported.

## Decisions

### 1. Three outcomes for a row, and no fourth

| The row                                                                                              | What the source does                                                    |
| ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Cannot be built into a valid record                                                                  | Emits no record; reports a finding on the licensing authority           |
| Is built, with a value corrected, replaced or left off                                               | Emits the record with the finding on it                                 |
| Is bad in a way good data cannot be                                                                  | Throws; the command stops and names the source, the row and the problem |
| Is read but not selected (names no officer the database knows, is outside the source's stated scope) | Counts it under a named reason and logs the counts                      |

"Cannot happen in good data" is decided per case and written down in the source's spec. The test is whether the source's real data has ever shown the condition. The TCOLE workbook of 2025-02-10 has no blank `DEPARTMENT_NUMBER`, `PUBLIC_GUID`, `LICENSE` or `LICENSE_ACTION` in any of its four sheets and no repeated department number or officer GUID, so a blank ID there throws.

### 2. Which licensing authority

The finding goes on the licensing authority the row's data belongs to:

- a licensing source (TCOLE, Minnesota POST, Oregon DPSST) reports on its own authority;
- any other source reports on the licensing authority of the state of the agency the row is about, the rule `move-complaint-summaries-to-generate` already uses for a docket.

When a source cannot tell which state a left-out row belongs to, it throws. A finding is never attached to an arbitrary record. The source emits each authority it may report on every time it runs, with an empty list when it has no findings, so that an earlier annotation is resolved.

### 3. What a finding holds

The fields `record-findings` defines: a code that names the sort of problem, the type, the field, the value found, a plain-English message, the source namespace, the source record ID, and evidence. For a left-out row the source record ID is the row's own ID in the source (a docket ID, a license number, a workbook row), and the evidence is one source record that says where the row can be seen. A row with no ID of its own uses the file name and row number.

The row number need not be perfect; it must be stable and predictable (owner's decision, 2026-11-17). When a table lists the newest row first, its rows are numbered from the oldest: the last row is 1. A row added at the top then changes no earlier row's number. When the table runs over several page files, the count runs through all of them from the last row of the last page, and the name is the one the pages share without the page number, because a new row can move an earlier row to the next page. Oregon DPSST employment findings are named `officer-<DPSST number>-employment#<row>` this way. The evidence still gives the page file and the row's place on that page.

### 4. Row accounting

`SourceManifest` gains `accounting`: for each input the transform reads, the number of rows read, emitted, reported, and not selected by reason. The shared transform step fails when read does not equal the sum of the others, and writes the totals as the transform's last log line. `org/policeconduct/manual` has no source rows; it counts each record it reads from its manual output in state as read and emitted, and states zero when there is none. This is what turns a future bare `continue` into a failed command.

A row that feeds several records (a TCOLE officer row feeds `Personnel`, licenses and assignments) is counted once, at the sheet it was read from. A row left out because the record it depends on was left out is counted as reported under the first row's finding and gets no annotation of its own.

### 5. Calls that fail are not part of this change

A request that fails for one agency during an acquire is logged and counted today, and the cache of call results (`cache-call-results-and-files`) decides when it is tried again. That rule stands. This change covers rows and inputs, and the acquire conditions that are data problems, not service problems.

## Alternatives considered

- **Write left-out rows to `source_exclusions`.** Rejected in `move-complaint-summaries-to-generate` for the same reason: that field records a person's decision to exclude a record and has no place for a reason code, an address or evidence.
- **Log every left-out row and write no annotation.** Rejected by the owner: a log is not visible to a reader of the site, and a gap in the public record must be.
- **Only fix the known cases, with no accounting.** Rejected: the next source would repeat the fault and nothing would catch it.

## Risks and mitigations

| Risk                                                                                 | Mitigation                                                                                                            |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| A source that has been dropping rows quietly now produces many public annotations    | The validation task reports the count by source and code before merge; the owner decides the wording of each message. |
| A condition judged impossible turns out to exist in a later file and stops a rebuild | The error names the source, row and problem. Moving the case from "throw" to "finding" is a one-line spec change.     |
| Row accounting miscounts a row that feeds several records                            | The counting rule is fixed in decision 4 and each source has a test with an independent expected count.               |
| A national source cannot name a state for some rows                                  | It throws, naming the row; the owner then decides where that source's findings belong.                                |
