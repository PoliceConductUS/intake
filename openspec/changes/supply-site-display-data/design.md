## Context

Website commit `84c5cec` removed every content and relationship decision from the website. The inventory `site-decisions-inventory.md` and the queue `intake-corrections-queue.md` list what the site used to compute. Two kinds of site logic remain on purpose:

- **Page-selection rules**, kept by the owner, to move into database views where possible.
- **Build projections**, written by the website script `scripts/refresh-build-projections.mjs` into `public.build_page_payload`, `public.agency_zip_index` and `public.location_path_closure`. The owner asked on 2026-11-22 to move these and every public count into the database.

The script today does this, in one transaction:

1. Selects agencies that have at least one current `agency_personnel` row (by the website predicate `currentAssignmentSql`: null `end_date`, null effective end date in `data_source_values`, start date not in the future) and whose place sits under an `administrative_area` row under a `state` row.
2. Counts, per agency: distinct current personnel, distinct reports through `review_personnel`, distinct civil cases through `civil_case_personnel`.
3. Groups agencies into states, areas and places. It derives the area kind and plural ("County", "Parishes") from name suffixes, prefers a non-all-caps city label, averages agency coordinates into place, area and state map points and pads bounding boxes.
4. Counts reports per location by exact `reviews.location_path_id` and civil cases per location by `path like prefix%` over agency locations.
5. Builds report rows, taking the report's agency from the first `review_personnel` row and state, area and place slugs by `split_part` of the path.
6. Rewrites `location_path_closure` for eligible locations, `agency_zip_index` from the first five ZIP characters (dropping `00000`), and `build_page_payload` as JSON per state, area, place, agency and report page, with a SHA-256 content hash.

Intake rules that apply: data enters the database only through envelopes and recorded mutations; `data up` never calculates; IDs come from the source-name mapping; manual records come from `org/policeconduct/manual` (ADR 0031); findings become annotations (ADR 0040); annotation messages move to a message table (ADR 0038).

## Goals / Non-Goals

**Goals:**

- Every fact the site shows is a stored column or a row filled by intake.
- Every page-selection rule, foreign-key chain and public count is one SQL definition in an intake migration.
- The website build only reads tables and views.
- Every text standardization is recorded as a correction annotation.

**Non-Goals:**

- Website code changes. They are listed under "Website follow-up" as a cross-repo note.
- Arrest data. The change `import-arrest-records` replaces `arrest_profile` and `agency_arrest_profile`.
- Records with a known agency and an unknown officer. The change `unknown-officer-records` covers them.
- Release news selection (preferred coverage copy, alias target) and roster provenance copy. See "Open Questions".

`administrative_area_kind` is a manual-records table: `id`, `name` (for example `County`, `Parish`, `Borough`, `Census Area`), `plural_name` (`Counties`, `Parishes`). It replaces the suffix rules in the projection script.

Status columns hold the reader-facing word. The site shows it as stored. The alternative, a lowercase code plus a label table, adds a join for three fixed values; it is listed as an open question.

`reviews.agency_id` records the agency the report is about, as the report source states it. It is not taken from `review_personnel`. A report may name officers at other agencies; the agency column is still one recorded fact.

### D2. Employment status rule (intake's documented rule)

Intake sets `employment_status` per assignment from what the source says:

- `Former` when the assignment has an `end_date`.
- `Current` when the assignment has no `end_date` and the source is a roster of current staff that lists the assignment in its latest acquired snapshot (for example the TCOLE current appointments and the MN POST current roster, which already emit `end_date` null explicitly).
- `Unknown` in every other case.

The rule is written in `docs/` and in each source's README. Each source states which of its inputs is a current roster. A value is a resolved property, cached through the `ResolvedProperty` adapter. Because `intake-date-validation` already omits future dates, no "start date after today" case remains.

The effective date substitution the site used (`data_source_values->effective_value` for a null date) stops. Intake writes the effective date into `start_date` and `end_date`. If a source supplies a date only as unparseable text, the column stays null and the existing validation annotation keeps the original text.

### D3. Civil case status rule

- `Closed` when the source reports `date_terminated` or a final outcome.
- `Open` only when the source states the case is pending.
- `Unknown` otherwise.

This follows owner answer Q19: "pending and other states only when intake actually determined the state."

### D4. License action types

Two manual-records tables:

- `license_action_type`: `id`, `name` (the collapsed public label, shown as "License Action"), `category` with `check in ('discipline','commendation','other')`.
- `license_action_text`: `id`, `source_text` (the exact source action text, unique), `license_action_type_id` (not null).

`license_action` gains `license_action_type_id text not null references license_action_type(id)`. The shared import resolves it from `license_action.action` through `license_action_text` as a resolved property. An action text with no row fails generation with the text and the source record named. `license_action.action` keeps the source text.

The collapse is not decided. Task 3.1 lists every distinct source action text from the TCOLE, MN POST and Oregon DPSST transforms and proposes the smallest set of types. The owner reviews it before any row is written.

### D5. Annotation message codes

`data_annotation` gains `message_code text not null references data_annotation_message(code)`. `data_annotation_message` is a manual-records table: `id`, `code` (unique, stable, for example `standardized_text`), `message` (plain English, no markup). The site joins `message_code` to `data_annotation_message` and shows `message`.

The change `type-annotation-envelopes` already proposes the code and the table. If it is applied first, this change only adds the codes listed in the specs. If this change is applied first, it creates the column and table with the shape that change describes, and that change drops the duplicate task.

The finding code that ADR 0040 already gives each finding is the message code. Messages must not contain internal IDs or slugs (the current duplicate-exclusion message does).

### D6. Text standardization

A manual kind, `StandardValue`, holds one entry per exact value: subject kind, field, `source_value`, `standard_value`, and a reason. A shared stage in `data generate` applies the entries after property corrections and before validation. For each record whose field equals a `source_value`, the stage writes `standard_value` and adds a correction finding with message code `standardized_text`. The shared import turns it into a correction annotation, with the original value and the replacement value. Raw inputs and `data_source_values` keep the original.

For enumerated columns (`license.status`, `license_action.status`, `agency.status`) an unknown value fails generation, as for license action texts.

For free text (all-caps `agency.name`, `agency.contact_name`, `location_path.display_name`), entries are written per exact value. A script proposes title-case values for review; no automatic title-case rule runs in the pipeline, because a rule gets names such as "At Law" wrong.

The entries are manual records, not code. No namespace, kind or source ID is special-cased in code.

### D10. What cannot move to the database

- **Sorting with the website's `Intl.Collator` (numeric, base sensitivity).** Sorting is formatting, allowed to the site. Views do not promise an order.
- **Count phrases** such as "3 places" or "agencies located here". These are copy built from a count; they stay site formatting.
- **Map bound padding** (18 percent, at least 0.02 degrees). It is presentation; the view returns the stored bounding box.
- **`NO_PERSONNEL`.** A build setting, not content.

### D11. Which page shows an annotation

Owner decisions, 2026-11-22 (the last one replaces the two before it): first, "intake attaches every annotation about a person to the licensing authority"; then, "an annotation on a link between two records shows only on the licensing authority's annotations list"; then, authoritative: "link annotations prefer attaching to humans - if no human is a linked record then agency, then licensing authority page only."

The rule intake applies, for every annotation, from the records its subject connects (resolver-registry `annotationPageResolvers`, `src/cli/import/artifacts/facades/annotation-page.ts`):

1. A linked person: set `data_annotation.personnel_id`. The person's page shows it.
2. Else a linked agency: set `agency_id`.
3. Else the record whose page shows it: `review_id`, `civil_case_id`, `location_path_id` or `federal_agency_id`.
4. Else the licensing authority only: `licensing_authority_id`.

Exactly one attachment column is set (`data_annotation_one_attachment` allows at most one; `assert_site_projections()` raises on an active annotation with none until the later migration in task 9.11a makes it a check). `subject_kind` and `subject_id` stay the audit link to the record the finding is about. ### Annotation read shape

Owner direction, 2026-11-22: "the annotation should be generated such that when it is written to the database and later read by the site, it contains exactly the human readable information needed for the page - e.g. a type, a message, a list of links (to connected records) as build target urls not ids, labels for each url - no encoding meaning into fields ending in _id."

- **Links.** `data_annotation.links jsonb`: a non-empty array of `{"url": <site path or null>, "label": <text>}` in display order. A url starts and ends with `/` and may end with `#fragment`; null means the connected record has no page of its own. The check `data_annotation_links_check` (function `data_annotation_links_valid`) enforces exactly these two keys. A jsonb array on the annotation row was chosen over a child table `data_annotation_link`: the links are written in the same envelope and mutation as the annotation (one write path, no second record kind with its own stable IDs), are always read whole, and the check constraint gives the same shape guarantee.
- **URLs** are built by intake from stored canonical paths and slugs: `/personnel/{slug}/`, `{place path}{agency slug}/`, `{location path}reports/{yyyy}/{mm}/{dd}/{slug}/` (UTC incident date; null url when the date is missing), `/civil-cases/{slug}/`, the location `path`, `/federal/{slug}/`, `{state path}licensing-authority/` (null url when the authority's location is not a state). Labels are the person's full name, the agency, federal agency or authority `name`, the report or case `title`, the location `display_name`.
- **When a target's path changes.** Intake derives `links` and the attachment whenever the producer supplies none, which is every intake-produced finding, on every `data generate`; compare-then-write updates the stored row. A published slug never changes. A url that is no longer a page path at refresh time (for example an agency that lost its page) is returned by `site_annotation` with a null url, so the label shows without a broken link; the next generation of the annotation's source rewrites the stored url. A producer-supplied value (including an explicit null) is kept as supplied.
- **Shown values.** The page shows reported and replacement values today, so `display_value` and `display_replacement_value` stay: plain text, null for JSON null and for a field that holds an internal reference (`id`, `*_id` other than `source_*`), the excluded record's name for `excluded_records`; the replacement only for corrections. This is the website's former `annotationDisplay` rule, moved into intake.
- **Type and message.** `site_annotation.type_label` comes from `data_annotation_type` (manual records; the `data_annotation.type` foreign key is added with the records, task 9.11a). The message is `data_annotation.message` until message codes (D5) exist; `site_annotation` then reads `data_annotation_message`.
- **What the site renders.** `site_annotation`: `page_path`, `page_type`, `licensing_authority_path`, `type`, `type_label`, `message`, `links`, `display_value`, `display_replacement_value`, `source_namespace`, `source_record_id`. No field name, evidence or ID column is in the view.

### D12. Personnel headline assignment

**Done (owner, 2026-11-22).** The migration `supabase/migrations/20261122200000_site_personnel_headline_assignment.sql` creates `site_personnel_headline_assignment`: one row per person with at least one `agency_personnel` row, naming the assignment the personnel page title, hero, `/personnel/` list structured data, form prefills and schema.org `worksFor` use. It is the website's former `selectHeadlineAssignment` rule, moved. Columns: `personnel_id`, `agency_personnel_id`, `agency_id`, `title`, `badge_number`, `employment_status` (from `site_agency_personnel_employment`), `end_date` and `headline_basis`.

- `Current`: the person has a `Current` row; the row is the `Current` row with the latest start date.
- `Recorded`: no `Current` row and at least one `Unknown` row; the row is the row with the latest start date.
- `Most recent`: every row is `Former`; the row is the row with the latest end date, then the latest start date.

Dates are the stored column, or the `data_source_values` effective value when the column is null and the value is a real calendar date. An absent start date sorts first; remaining ties go to the greatest `id`.

### Measured cost

Local database, read-only, 2026-11-22: 3,457 agencies, 162,629 personnel, 216,469 `agency_personnel` rows, 551 civil cases, 3 reports and 452 annotations. 57,126 place, 3,144 area and 51 state `location_path` rows. Every state and area row has a `centroid` and a `bbox`.

- Whole-view scans: `site_agency_count` 0.2 s, `site_personnel_count` 0.3 s, `site_personnel_state_count` 0.8 s, `site_personnel_headline_assignment` 1.5 s.
- One person from `site_personnel_headline_assignment` by `personnel_id`: 0.32 s. The filter does not reach inside the window function, so each call scans every assignment. For 162,629 personnel pages, that is about 14 hours per build.
- One agency from `site_agency_count` by `agency_id`: 0.2 ms.

### Options

- **A. One wide JSON row per page.** Every list on the page is aggregated into the row as JSON. This is what `build_page_payload` is today.
- **B. Composable page views.** One row per page with plain columns. Each list on a page is read from another view, filtered by a parent-path column.

Trade-offs:

- **One wide view against composable views.** A wide row needs one query per page. But a list row (for example an agency with its counts) is defined again inside each parent that lists it. Composable views need two to five queries per page, each `where <key> = $1`. A list row is defined once and reused: the agency row on its own page, its place page and its federal page is the same row.
- **JSON against child views.** JSON is untyped, makes big rows for large rosters, and is hard to test column by column. Its array order is a sort the site redoes with `Intl.Collator` anyway (D10). Child views keep typed columns.
- **Materialized against plain views.** A plain view is always current and needs no refresh. But where a rule uses a window or an aggregate, each page query pays for the whole view (see "Measured cost"). A materialized view costs one refresh per build, a few seconds in total, and gets an index on each key. It also fixes "today" at refresh time, so every page in one build uses the same date. The costs: a refresh step that can fail, and intake writes after the refresh are not seen until the next refresh.
- **`build_page_payload`.** Kept as a JSON table, it is a second copy of the page views. Its two real jobs are the list of pages and the check that no two pages claim one path. `site_page` does both.

### Recommendation

Option B, with materialized page views. Two layers:

1. **Rule and count views** stay plain views and stay the one definition of each rule: `site_agency_personnel_employment`, the `site_*_count` views (D8), `site_personnel_headline_assignment` (D12), and the new `site_location_ancestor` and `site_location_count`.
2. **Page and list views** are materialized views. They read layer 1, tables, and page views refreshed before them (for example a list's `agency_path` comes from `site_agency_page`, so "has a page" is defined once). Each has a unique index on its own key and a btree index on each parent-path column. A loader runs `select * from site_<page> where path = $1`, then one `select * from site_<list> where <parent>_path = $1` for each list on the page.

The D7 selection views become these page views. They keep their names and rules, and now carry every column the page renders. `public.refresh_site_projections()` (D9) refreshes layer 2 in dependency order and then runs the checks. `site_page` replaces `build_page_payload`.

A page view is also the list view for its parent. A place page lists `site_agency_page where place_path = $1`. An area page lists `site_location_page where parent_path = $1`.

Each page view returns the page's route segments and its stored identifying values: `segment` for a state, area or place, and `slug` for an agency, person, federal agency, report or civil case. `getStaticPaths()` and the help-collect link (`buildHelpCollectHref` in `civic-index.ts`, `CivicScopedOverviewPage.astro`, the agency page) read these columns and split no path. Views promise no order (D10).

**Why paths are split today, and what replaces each split (owner, 2026-11-22):**

1. `sitemap-lastmod.js` groups last-modified dates by state with `split_part(lp.path, '/', 2)`. Replacement: the stored `state_code` on the state row plus the parent chain, exposed by `site_location_state`. `site_page` carries `state_path` and `state_code`, so the sitemap groups by a column.
2. `generate-redirect-map.mjs` builds old-site URLs by taking the state from the current path. Owner decision (2026-11-22, final): redirects are derived by the website build, not stored. The build takes the previous release's `sitemap.xml`, removes URLs present in the new build, reads each remaining old page (from production or `<commit>.release`) to find its record from the entity kind and id embedded in the page's ld+json, and redirects to that record's page in the new build; no target gives 404. Old pagination URLs map through the first record listed on the old page; old video URLs are ignored. Intake's part: `site_page` carries `entity_kind` (the intake record kind) and `entity_id` for every page, so the website can embed them. No redirect table and no `redirects.json` pairs are stored.
3. `civic-index.ts` takes the help-collect query value from the last path segment. Replacement: the stored `segment` or `slug` column in the page view.

Where the implementation differs from the table above:

- **One row = everything the page container needs (owner, 2026-11-22).** `site_personnel_page` carries the path, the person's names and `full_name`, `deceased_on` and `deceased_message`, the headline assignment by the D12 rule computed inside the view (`headline_*`, `headline_basis`), `works_for_agency_name` and `works_for_agency_path` (set only when the headline is Current, the schema.org `worksFor` rule), the counts, `page_title` and `page_description` (the website's wording moved, with dates as `Mon D, YYYY`), the headline agency's `state_path` and `state_code`, and `lastmod`. `site_personnel_headline_assignment` stays until phase B switches the personnel page (task 9.16 drops it). The other page views carry every stored column and count their page renders; page titles of the other page types are still built by the website from these columns.
- **Area kind and plural** are not in `site_location_page`: `location_path.administrative_area_kind_id` (D1, tasks 2.1 and 2.8) is not built.
- **Report agency** is not in `site_report_page`: `reviews.agency_id` (D1, task 2.5) is not built. The agencies of the linked personnel are in `site_report_personnel`. `site_agency_page.report_count` keeps today's rule (reports linked through `review_personnel`).
- **License actions** group by the source action text in `site_licensing_authority_count` until `license_action_type` exists (task 3).
- **Annotation message** is `data_annotation.message` until message codes exist (D5).
- **Entity kind and id per page.** `site_page` has `entity_kind` (the intake record kind) and `entity_id` for every page; a topic or report archive page names its scope's record. The website embeds them for its redirect derivation.
- **Required values.** No migration fills rows. The rules "every row has a segment", "every state row has a state code", "every active annotation has one attachment and links" and the `data_annotation.type` foreign key become constraints in later migrations after a `data reset` fills them (tasks 9.2a and 9.11a). Until then `assert_site_projections()` raises on them, so `refresh_site_projections()` fails on a database whose rows were written before this change: on the shared database it fails with "location_path rows whose path is not the parent path plus segment: /ak/, ...".
- **Duplicate path.** `refresh_site_projections()` catches the unique violation on `site_page` and raises "Two pages claim one path: Key (path)=(...) is duplicated."
- **Checks not built:** "a report without an agency" waits for `reviews.agency_id`; "an agency without a location path" is already prevented by `agency.location_path_id not null`. Added checks: a review without an incident date (it has no report page), a state row without `state_code`, an active annotation without links or an attachment, an annotation type without a label.

## Risks / Trade-offs

- [The new `NOT NULL` columns need values for every row] → Filled by regenerating all sources in `data reset`. No migration backfills rows.
- [Employment status from sources that do not say "current"] → Those assignments become `Unknown`, and agencies whose only assignments are `Unknown` lose their agency page. Task 2.2 counts them before the reset, and the owner reviews the list.
- [Report counts change meaning] → Today an agency's report count follows `review_personnel`; with `reviews.agency_id` a report counts once, under its recorded agency. The difference is reported before release (task 6.4).
- [Location personnel counts change meaning] → Today a place sums agency counts, so a person at two agencies counts twice. The view counts distinct people. Reported before release.
- [Materialized views can be stale] → The build refreshes them before it reads. A refresh failure fails the build.
- [The website breaks between the intake release and the website follow-up] → Accepted by the owner; fixed afterward.
- [Materialized page views add refresh time to each build] → Measured at a few seconds for the current count views; task 9.14 measures the full refresh. Plain page views would cost about 14 hours for personnel pages alone.
- [Page views and the projection script run side by side during the switch] → New views read tables and layer 1 only, never `build_page_payload` or `location_path_closure`, so each website page type can switch alone. `site_personnel_state_count` moves off `build_page_payload` in task 9.4.
- [Many standard-value entries for all-caps names] → Proposed by a script, reviewed in bulk, written through the manual source.

## Migration Plan

1. Land migrations in this order: manual-records tables; new columns; standard values; views; materialized views and functions; drop the old projection tables.
2. Add the manual records (license action texts and types after owner review, messages, administrative area kinds, standard values).
3. Run `data reset` against a database with no other rebuild in progress.
4. Run the integrity assertions in tasks 7 and 9.
5. Switch the website one page type at a time (tasks 9.3 to 9.13), then drop the projection tables (task 9.14).
6. Rebuild production the same way, then deploy the website follow-up.

Rollback: revert the migrations and run `data reset` from the previous commit.
